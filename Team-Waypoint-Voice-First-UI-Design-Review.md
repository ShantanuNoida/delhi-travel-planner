## 0. What the docx asks for that the app already does (no action needed)

Confirmed present in the current code, so not re-reported:
- Voice + touch parity, text never harder to reach than voice (R-29/R-33)
- Tiered confirmation for bulk/vague edits — "relax whole trip" previews and asks yes/no before committing (M2, Phase 1 QA)
- A listening state, a transcribing state, and a thinking state, all visually distinct (R-20, Listening Indicator round)
- The itinerary renders as a scannable timeline (day tabs, clock times, map with route line) that voice edits visibly update (R-23/R-25)
- Constraints the user can't see (travel time, opening hours, over-packed days) are surfaced as badges/captions (R-24, day-balance notes)
- A manual-entry (text) fallback for anything voice fumbles, always visible, never demoted behind an extra click (R-29)
- A clear, unambiguous "mic is live" indicator (R-30, Listening Indicator round)

## 1. New findings

**Implementation status (2026-08-12): all three HIGH findings below are implemented and verified.** Full regression clean after all three (Phase 2 8/8, Phase 3 8/8 agent + 4/4 narrator, Phase 4 6/6 + guards 5/5, Phase 5 8/8, Phase 6 5/5), plus a new 35-check deterministic verification script (`verify_high_findings.py`, no LLM calls except one real POI search exercised end-to-end) covering `resolve_stop_reference`'s unique/ambiguous/none cases, `apply_edit()`'s `needs_choice` contract, the undo stack (push/pop/cap), `resolve_pending_choice()` committing the *chosen* candidate specifically (not the other ambiguous one), ordinal-reply parsing, and the conversational "undo" command (including a word-boundary check so "undoubtedly" doesn't false-positive). The running app was also boot-verified (clean `HTTP 200`, zero tracebacks in the server log). MEDIUM/LOW findings and the theme proposal remain unimplemented, pending direction.

### HIGH — No review step for what the mic heard before it's acted on
**Docx says:** *"Use visible transcription of what was heard so the user can spot errors ('Nice' vs 'Nikko') at a glance."*
**What happens now:** `phase6/app.py`'s mic handler transcribes the clip and calls `_send(heard)` in the same breath (`app.py:461-466`) — the transcribed text is appended to the transcript and handed straight to `agent.process_turn()` in one atomic step. The user sees what Whisper heard at the exact moment the agent is already acting on it, not before. If Whisper mishears "Nikko" as "Nice" (the docx's own example), there is no window to catch or correct it before an edit is applied or a build kicks off.
**Fix direction:** surface the transcribed text in the existing `listening_slot` banner *before* dispatching it — e.g. "Heard: **'add Nikko to day 2'** — sending…" with a ~1-2s beat (or a one-tap "✕ that's wrong" to cancel before send fires), rather than silently going straight from audio to committed action. Doesn't need to block every turn behind a manual confirm (that would undermine voice-first speed) — just needs the words on screen a beat before they're acted on.

### HIGH — Ambiguous matches fail silently instead of offering tappable choices
**Docx says:** *"If 'add a museum near the hotel' returns three candidates, show three tappable cards instead of reading options aloud one by one — resolving choice is far faster by eye than by ear."*
**What happens now:** `phase4/edit_engine.py`'s `_find_stop_by_name()` explicitly returns `None` on anything but an unambiguous match ("a substring match is only trusted when it's UNAMBIGUOUS... ambiguous partial matches return None rather than risk swapping the wrong one" — `edit_engine.py:269-272`), and the swap/add search paths pick a single best-ranked POI without ever surfacing runner-up candidates. Both are safe (no wrong-guess edits), but every ambiguous case degrades to a generic "couldn't find a suitable match" text response — never a visual pick-one moment. This is a structural gap, not a bug: the option to *ask the user to choose* doesn't exist anywhere in the pipeline yet.
**Fix direction:** when `_find_stop_by_name()` or a swap/add search has 2-4 plausible candidates instead of one, return them instead of `None`, and have `app.py` render them as small tappable cards (name + category + thumbnail, reusing the existing stop-card component) in the confirmation banner slot — a lightweight version of the CONFIRM Yes/No banner pattern (`UX3-1`) already built for the build-confirmation step.

### HIGH — No undo / edit history
**Docx says:** *"Design a strong, always-available undo and an edit history. Voice errors are inevitable; recovery must be trivial."*
**What happens now:** grepped the whole codebase — there is no undo mechanism anywhere. Every prior round's strategy for a *bad* edit has been prevention (feasibility/correctness guards that reject and roll back before committing — E-1, M1, M2), which is good, but there's nothing for a *successful* edit the user simply regrets or a misheard command that passed all the guards (e.g., a legitimate but unwanted swap). The only recovery path today is issuing another edit command to manually reconstruct the prior state.
**Fix direction:** `TravelAgent` already mutates `self.itinerary` as a single dict on each committed edit — cheapest version is a small stack of prior itinerary snapshots (cap at ~5-10 to bound memory) pushed right before each commit, plus one always-visible "↩️ Undo last change" control near the itinerary panel. Doesn't need a full history browser to start; even one-level undo closes most of the gap the docx is flagging.

**Implementation notes for the three HIGH findings above:**
- **Voice review-before-send:** went with a real gate rather than a timed pause — a timer can only delay noticing a bad transcription, not prevent it acting, and the docx's "before they compound" implies prevention. `phase6/app.py`: mic transcription no longer calls `_send()` directly; it stores the heard text in `st.session_state.pending_voice_text` and reruns. A banner rendered into the existing `listening_slot` placeholder (so it still appears above the fold, under the mic) shows the heard text with **✅ Send** (primary — a correct transcription is still one tap), **✏️ Edit** (prefills the text box via a new `voice_edit_prefill` → keyed `main_text_input` session-state handoff), and **✕ Discard**. Typed input is untouched.
- **Ambiguity → tappable choices:** `phase4/edit_engine.py`'s `_find_stop_by_name()` was split into `resolve_stop_reference()`, which reports `unique` / `ambiguous` / `none` instead of collapsing the last two into the same `None`; the old function is now a thin back-compat wrapper so no other caller's contract changed. `apply_edit()` intercepts an `ambiguous` swap-target match and returns `needs_choice: True` + up to 4 real candidates instead of guessing or falling through to a broad, wrong-scope edit. `phase3/agent.py` gained `pending_choice` state, a `resolve_pending_choice(index)` method, and a `_commit_edit()` helper (extracted from the main EDIT-turn path, which now also serves the choice-resolution path so both share identical correctness/feasibility guards). `phase6/app.py` renders the candidates as bordered, tappable cards in the itinerary panel — resolved instantly, no LLM roundtrip. A spoken/typed ordinal reply ("the first one", "2") also resolves it via `_parse_ordinal_choice()`, so the flow isn't UI-only.
- **Undo:** `TravelAgent` gained `itinerary_history` (capped at `MAX_UNDO_HISTORY = 8`), `push_itinerary_snapshot()`, and `undo_last_edit()`. Wired into every commit path — the main edit flow, the M2 whole-trip-relax preview's "yes" commit, `resolve_pending_choice()`, and `app.py`'s ↑/↓ move buttons — plus a word-boundary `"undo"` conversational command (mirroring R-41's `"stop"` word-boundary fix so `"undoubtedly"` doesn't false-positive) that works without an LLM call. An "↩️ Undo last change" button appears in the main itinerary panel whenever there's something to undo.
- **Verification:** a new 35-check deterministic script (no LLM calls except one real POI search exercised end-to-end) covers all of the above, including that `resolve_pending_choice()` swaps the *chosen* candidate specifically, not the other ambiguous one. Full regression clean (Phase 2 8/8, Phase 3 8/8 + 4/4, Phase 4 6/6 + guards 5/5, Phase 5 8/8, Phase 6 5/5); the live app was also boot-verified (clean HTTP 200, zero tracebacks).

### MEDIUM — No anaphora / pronoun resolution across turns
**Docx says:** *"'Move it earlier' should know what 'it' is. Anaphora resolution and short-term memory of the current focus are essential for natural voice flow."*
**What happens now:** grepped `phase3/agent.py` and `phase4/intent_classifier.py` — no pronoun/anaphora handling exists. Every edit command must fully re-specify a day/slot/name; "move it earlier" or "swap that for something else" referring to whatever was just discussed has no path to resolve.
**Fix direction:** track a lightweight `last_referenced_stop` (day/slot/name) on `TravelAgent`, updated whenever an edit targets a specific stop or the user asks about one by name, and have the classifier prompt include it as context so "it"/"that"/"this one" can resolve when no explicit target is stated in the current turn.
**✅ Implemented (2026-08-12).** Went with a text-rewrite approach instead of threading context into the classifier's LLM prompt (cheaper, deterministic, and testable without burning quota): `TravelAgent.last_referenced_stop_name` is set after a named swap/add commits (parsed from `edit_engine.py`'s own fixed message format, e.g. "Swapped: X → Y" → tracks Y) and after an EXPLAIN turn that unambiguously mentions exactly one real scheduled stop. A new `_resolve_anaphora()` rewrites a deliberately narrow set of sentence-initial templates ("swap it for...", "remove it", "tell me more about it", "is it worth it/open/free/safe", "how much is/does it...", "when is/does it...") to substitute the tracked name, run right before `classify_intent()` — the user's original wording is untouched in the transcript/history. Each pattern must match the **whole** message, so it can't corrupt an unrelated sentence that merely contains "it" (verified against "make it more relaxed" and "is it going to rain" specifically). A real bug was found and fixed during verification: two of the six templates dropped the space between the resolved name and the rest of the sentence ("is Red Fortworth visiting") because their capture groups start at different points depending on whether a `\s*` before them had already consumed the separator — normalized in one place rather than fixing each pattern individually.

### MEDIUM — Edited stops aren't visually flagged in the itinerary panel itself
**Docx says:** *"...inline highlights on whatever just changed so the eye is drawn to the edit."*
**What happens now:** a successful edit gets a text confirmation in the Transcript column, but the stop card that actually changed in the main "Your Itinerary" panel looks identical to every untouched card — no highlight, badge, or brief visual pulse marks it. A user whose eyes are on the itinerary (not the side-rail chat) has no visual cue where the edit landed.
**Fix direction:** track the day/slot/index of the just-changed stop after a commit and render a subtle one-render highlight (accent-colored left border or a small "✨ Updated" chip) on that specific card — clears on the next interaction, same transient-state pattern already used for the "Speaking your reply" cue (R-32).
**✅ Implemented (2026-08-12).** `TravelAgent.last_changed_stops` holds `(day_key, slot, idx)` for every stop present after a commit but not before (matched by `osm_id`, computed generically across whatever `apply_edit()` reports as `changed_days` — works for swap/add without special-casing each edit type, and naturally yields nothing for a pure removal or reorder, which is correct since nothing new appeared). Cleared at the start of every `process_turn()` and at the start of `resolve_pending_choice()` (the UI's tappable-card path, which doesn't go through `process_turn()`), so a highlight only ever reflects the edit that just landed — exactly the "clears on the next interaction" requirement. `phase6/app.py` renders a `:green[✨ Updated]` chip inline next to the stop's name when its `(day_key, slot, idx)` is in the set.

### MEDIUM — No adaptive, per-context example prompts; "what can I say" is a single static line
**Docx says:** *"Surface contextual example prompts on screen that change based on where the person is ('Try: make day 2 more relaxed' while viewing day 2)... Offer a persistent but unobtrusive 'what can I say here?' affordance. After each successful action, occasionally suggest the next natural voice command rather than leaving dead air."*
**What happens now:** post-build discoverability is one fixed caption ("💬 Want changes? Try 'make day 1 more relaxed'...", `app.py:526-529`) that never changes regardless of which day tab is open, and there's no expandable full command reference, and no post-action "you could also try..." nudge.
**Fix direction:** three small, independent pieces — (1) swap the static caption's example for one derived from the currently-open day tab ("Try: make Day {N} more relaxed"); (2) a small "❓ What can I say" popover/expander near the input listing categories of commands (edit, ask, bulk-restructure) rather than one example; (3) after a successful edit, occasionally append one contextual suggestion to the agent's own reply (e.g., after a swap, "Want me to check the new stop's opening hours?"). None require new LLM calls if built as static/templated copy keyed off existing state.
**✅ Implemented (2026-08-12), all three pieces.** (1) Streamlit's `st.tabs()` renders every tab's content in the same script run (the browser just shows/hides them — there's no server-side "which tab is active" signal to key off), so the Day-N-specific caption is written **inside each tab's own block** instead — the user still only ever sees the one matching their open tab, which is what actually matters. (2) A `st.expander("❓ What can I say")` sits under the (now generic) persistent reminder, listing real edit/ask/undo/bulk-change examples grouped by category. (3) `_EDIT_TYPE_NUDGES` (in `phase3/agent.py`) appends one natural follow-up per edit type (swap/add/remove/reduce_travel), tracked via `_nudged_edit_types` so each type only nudges once per session — verified a second `remove` in the same session does *not* repeat the nudge, matching the docx's "occasionally," not every time.

### MEDIUM — Voice-only users cannot reorder stops at all
**Docx says (trust/control/accessibility):** *"...lean into voice's genuine accessibility strength... ensure the audio-only path is complete, not a degraded afterthought."*
**What happens now:** `E-3`'s fix made reordering an honest, working feature — but only via the ↑/↓ buttons on each stop card (`UX3-5`), which are mouse/touch-only. There is no spoken equivalent ("move Humayun's Tomb earlier" / "swap the order of my morning stops"). A user relying purely on voice — exactly the accessibility case the docx calls out by name — is fully blocked from this one capability, while a sighted/touch user is not.
**Fix direction:** add a real `reorder` edit type to `intent_classifier.py`/`edit_engine.py` (currently `_apply_reorder()` deliberately declines and points to the buttons) so "move X earlier/later" or "swap the order of Day N's morning and afternoon" resolves to the same `_move_stop()` logic the buttons already call.
**✅ Implemented (2026-08-12), scoped to the single-stop case.** `move_stop()`/`recompute_slot_times()` were relocated from `phase6/app.py` into `phase4/edit_engine.py` as the one shared implementation — `phase6/app.py`'s up/down buttons now import and call them from there, so a tapped button and a spoken command produce byte-for-byte identical results, not two parallel implementations that could drift. `intent_classifier.py`'s `reorder` schema gained `target_stop_name` (which stop) + `direction` ("earlier"/"later") extraction. `_apply_reorder()` performs a real move when both are present and resolve unambiguously; a whole-slot-order swap ("swap the order of Day 1's morning and afternoon") still has no single stop/direction to extract, so it correctly falls through to the original honest decline — broadening further risked silently moving the wrong stop, worse than "not yet" for a low-stakes feature. The existing budget/long-leg guards in `apply_edit()` apply to reorder edits for free (a move can change per-leg travel times via re-adjacency, so this isn't a no-op safety net). Verified: same-slot move, cross-slot-boundary move, the "already at the start of the day" edge case, and that the whole-slot-swap case is unaffected.

### LOW — No cost/budget-aware bulk edit
**Docx names this pattern directly:** *"'make this trip more budget-friendly'... should trigger meaningful restructuring, with changes shown for approval."*
**What happens now:** `E-4` made single-stop cost constraints ("swap for something free") an honest, specific decline rather than a silent failure — genuinely correct behavior for a single swap. But a *trip-wide* budget-reduction request has no path at all; the app has no cost-aware bulk-restructure capability, only pace-based ones (relax/tighten).
**Fix direction:** lowest priority here since ~27 POIs carry `kb_entry_fee` (a partial signal, per prior rounds' own note) — a real fix would need broader cost coverage in the dataset to be honest rather than best-effort; flagging for future scoping rather than recommending an immediate implementation.
**✅ Implemented (2026-08-12), scoped down from a full bulk-restructure to a real single-stop fix — the doc's own fix direction advised against forcing the bigger version.** The dataset now has 39 POIs with `kb_entry_fee` (grew from ~27), a handful explicitly tagged `"Free"`. Previously a cost constraint ("swap for something free") always failed 100% of the time — searching the literal text "free" as an interest category has no `INTEREST_MAP` entry, so every candidate came back fallback-flagged and got filtered out before pricing was ever consulted. Fixed at the source: a cost-worded swap/add now searches using the *old stop's own category* (the same pattern `_is_vague_replacement_constraint` already uses for "swap it for something else"), then requires an **explicit** `"Free"`-tagged candidate — an untagged POI (the vast majority, ~5,037 of ~5,076) is never assumed free just because nothing says otherwise, which would present a guess as fact, the one thing this app's grounding discipline exists to prevent. The decline message changed from "I can't filter places by price yet" (no longer true) to "I couldn't find a nearby option specifically tagged as free of charge — only a small number of places in my data have verified pricing, so I won't guess." A genuine trip-wide "make this more budget-friendly" bulk-restructure remains out of scope, as the original finding itself recommended.
**Verified** (mocked POI search, deterministic): a free-tagged candidate ranked *second* in the search results is still correctly selected over a paid one ranked first; when only paid candidates exist, the honest decline fires with the new wording; `_is_free_fee()` correctly distinguishes `"Free"`/`"Free (market area)"` from a real fee string and from a missing tag.

### LOW — Feasibility violations reject outright rather than offering the docx's suggested trade-off framing
**Docx says:** *"Warn conversationally ('that's three hours of driving between those two — want me to spread it out?')."*
**What happens now:** `E-1`'s fix (`_over_long_leg()`) is a hard guard — it rejects and rolls back an edit that would create a >45-min gap, with a specific message explaining why. Safe and correct, but more abrupt than the docx's conversational trade-off pattern (warn + offer an alternative like spreading the visit across two days), which the app already does elsewhere for budget overflows (M1's "would push day 2 over budget — I can replace an existing stop instead, or move this to another day"). Worth aligning `_over_long_leg()`'s rejection message to that same offer-an-alternative shape rather than a flat no.
**↩️ Corrected, not a live gap — no code change made.** Re-checked `apply_edit()`'s current guard block directly: the long-leg rejection message already reads *"That would leave day N with a long gap: ... I can pick a closer option instead, or move this to another day — want me to do that?"* — it already carries the exact offer-an-alternative framing this finding asked for (confirmed the budget-overflow guard right next to it does too). The original finding mischaracterized the current message; recorded honestly rather than "fixed" for a clean scoreboard, matching this project's established convention (see E-2, UI3-5 in prior rounds). One real, narrower gap *was* found while re-checking: the offer ("want me to do that?") isn't actually wired to anything — a "yes" reply doesn't trigger the alternative it names, unlike the M2 whole-trip-relax preview's yes/no flow. That's a different, new finding (making an existing offer *actionable*, not fixing its wording) and wasn't part of what was originally reported here, so it isn't implemented as part of this pass — flagged for a future round if wanted.

## 2. UI theme, buttons, fonts — proposal for a travel itinerary app

The app currently has exactly one deliberate brand decision: `primaryColor = "#C2540C"` (terracotta) in `.streamlit/config.toml`, applied to buttons/active-tab/checkboxes, plus a custom-CSS gradient on the single `<h1>`. Everything else (fonts, button shape, badge colors beyond the terracotta-tinted fee/hours pair, spacing) is Streamlit's framework default. `UI3-1`/`UI3-3` already flagged "no real type scale" and "one hue applied inconsistently" as open, un-implemented findings — this section proposes the actual system to close them, scoped for a **voice-first India travel product** (warm, trustworthy, non-corporate — not a generic SaaS dashboard).

A full interactive mockup (palette swatches, type pairing, button states, and a sample stop card in both light and dark) is published separately — see the artifact linked below — since color/type choices are far easier to evaluate by eye than by hex code in a markdown table.

**Typography:** pair a warm display serif for the brand title and day headers with a clean humanist sans for body/UI text — e.g. **Fraunces** (display, a touch of personality without being decorative — reads "travel guide," not "spreadsheet") + **Plus Jakarta Sans** (body — excellent legibility at small caption sizes, which matters given how much of this UI is dense metadata: opening hours, fees, travel times). Both are free Google Fonts, loadable via a CSS `@import` in the same `st.markdown()` block that already injects custom CSS — no new infra.

**Color system:** keep terracotta (`#C2540C`) as the one brand anchor — it's already validated across five rounds and shouldn't change. Extend it into a real scale instead of leaving every other color as a Streamlit default: a deep-indigo secondary (`#2D2A4A`-ish, evokes Indian textile/miniature-painting palettes without being literal-flag colors, same discipline R-26 already committed to) for links/secondary actions, keep the semantic greens/ambers/reds for grounded-data badges and warnings genuinely separate from brand hue (UI3-3 already made this call correctly for the time-of-day map markers — don't collapse those either). Add real light/dark parity — right now dark-mode users get whatever Streamlit's base theme does by default, untested against the custom CSS.

**Buttons:** move off Streamlit's flat-rectangle default toward a rounded-pill shape (`border-radius: 999px` on primary CTAs — mic button, Send, "Yes, build it") with a subtle elevation/hover shadow, consistent with the card-based, photo-forward direction rounds 4-5 already established. Keep secondary actions (Cancel/No/Retry) as outlined, not filled, so the visual hierarchy between "the thing I want you to tap" and "the escape hatch" stays obvious — this directly supports the docx's own confirmation-tiering guidance (§3 above): a high-stakes action's Yes button should look different from its No button, not just say different words.

**Cards/spacing:** the existing bordered stop-card pattern (R-23) is good and shouldn't change structurally — just tighten the type scale inside it (name in the new display face at a slightly larger size, metadata in the sans face) so the hierarchy reads instantly rather than relying on bold/caption weight alone.

**✅ Implemented (2026-08-12).** All of the above is now live in `phase6/app.py`'s CSS block, with one deliberate scoping decision: selectors were verified against the actually-installed Streamlit version's own compiled frontend (`1.57.0`) rather than assumed from generic Streamlit-theming examples, since `data-testid` naming has drifted across Streamlit releases historically and a guessed selector would silently no-op instead of erroring.
- **Fonts:** Fraunces, Plus Jakarta Sans, and JetBrains Mono loaded via a Google Fonts `@import` in the existing CSS block (this is a real running app, not a sandboxed artifact, so a CDN import is simpler than embedding font files and carries no CSP restriction). Fraunces applies to `h1`–`h6` (the brand title, `st.subheader()`'s section headers, and the trip-summary header band all pick it up automatically) plus a new `.wp-stop-name` span wrapping each stop's name specifically — the one place in the stop cards this round touched directly rather than only via a broad heading rule, so the mockup's "stop-name" role is actually realized, not approximated. Plus Jakarta Sans is the base body font; JetBrains Mono covers `<code>` spans and the new `.wp-time-chip` pill.
- **Colors:** terracotta is unchanged (still `#C2540C`/`#7A3608`, same as R-26); a deep-indigo secondary (`#332F5C`) and warm neutrals were added as CSS custom properties (`--wp-*`) with a `@media (prefers-color-scheme: dark)` override block, so dark-mode viewers get real, considered tokens instead of Streamlit's default dark palette colliding with the light-mode-tuned accent. Deliberately did **not** touch `.streamlit/config.toml`'s `[theme]` block to add these — doing so would force the whole app onto one fixed base theme, regressing R-26's explicit choice to let light/dark keep following the viewer's OS preference. The page background (`[data-testid="stAppViewContainer"]`) now uses the warm neutral instead of Streamlit's default; the sidebar/header chrome were deliberately left alone (out of scope — a partial re-theme of Streamlit's own chrome risked looking more mismatched than leaving it default).
- **Buttons:** `[data-testid="stBaseButton-primary"]`/`-secondary` (and their `FormSubmit` counterparts, which Streamlit gives a distinct testid suffix even when styled identically) now render as rounded pills (`border-radius: 999px`) with a hover lift on primary buttons and an outlined-not-filled treatment on secondary ones — covers the mic button, Send, Yes/No confirms, the Undo button, and the ambiguity-choice cards' "Choose this" buttons for free, since they all already use `type="primary"`/default secondary.
- **Not done, by design:** re-deriving the fee/hours badge colors from the new indigo secondary — they're already correctly on-brand terracotta tints from UI3-3 and changing them wasn't asked for or shown in the mockup.
- **Verified:** a direct logic-level check of the new `.wp-stop-name`/`.wp-time-chip` HTML string construction (correct escaping of a real apostrophe+ampersand test name); replayed the exact stop-card rendering logic against a **real** built itinerary (9 real stops, including "Karim's") with zero exceptions; the live Streamlit server boots cleanly (`HTTP 200`, zero tracebacks) both empty and — via the replay above — with the logic a populated state would exercise. Full regression clean (Phase 6 5/5; the rest of the suite is unaffected since this is presentation-only). Not verified: actual rendered pixels in a browser (no Playwright available this session) — the CSS itself, the escaping, and the exact real-data rendering path were all checked directly instead.
