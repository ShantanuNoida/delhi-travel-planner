## Post-Round Addendum 4 — Live user-reported failures, exploratory pass (2026-07-25)

**Trigger:** direct user report — "The application is not able to handle probing questions and edit instructions. Even swapping a place with another is not working well." This is a materially different investigation method from the rest of this document: instead of the templated 20-probe QA harness, Team Waypoint drove the real `agent.py` (the exact code path the Streamlit app uses) with **diverse, naturally-phrased commands** ("Can you swap the museum for something else?", "I don't really like Karim's, can you replace it with another restaurant?", "Swap Humayun's Tomb for Qutab Minar," etc.) rather than the harness's fixed wording — surfacing several real defects the templated probes had never phrased in a way that would trigger them. Full session log: `scratchpad/explore_log.md`.

### Findings and fixes

- **CRASH (CRITICAL) — a whole class of guard-driven EDIT→EXPLAIN reclassifications crashed with a raw `AttributeError`.** Real repro: "I don't really like Karim's, can you replace it with another restaurant?" returned the generic "Something went wrong on my end" fallback. Root cause: `classify_intent()`'s final `"query": data.get("query", text)` only falls back to `text` when the `"query"` key is *absent* from the LLM's JSON — not when it's present with value `null`. The classifier's own prompt tells the model to leave `query` null unless it originally classified EXPLAIN itself; whenever the **pre-existing H3 guard** (or this round's Q-2 extension of it) reclassifies EDIT → EXPLAIN *after* the model already committed to EDIT (and correctly left `query` null per its own instructions), the returned dict became `{"intent": "EXPLAIN", "query": None}`, which crashed `explain_engine.py`'s `query.lower()`. **Fix:** `data.get("query") or text` (one line). **Impact:** this bug predates this session — Q-2's guard extension earlier today only widened the net that triggers it. **Verified live**: exact repro now returns a real, grounded, honest answer instead of crashing.

- **"Swap X for Y" (naming both an old and new place) replaced the wrong stops entirely — the user's core complaint.** Real repro: "Swap Humayun's Tomb for Qutab Minar" left Humayun's Tomb completely untouched and instead swapped two unrelated stops (Karim's → "Tomb", Khan Market → Qutab Minar) elsewhere in the day. Root cause: the `edit_intent` schema had **no field for "which existing stop to replace"** — only `target_day`/`target_slot` (a position) and `constraint` (the new place). When a user identifies the old stop *by name* rather than by day/time-of-day, the classifier had no way to express that, defaulted to `target_day="all"`/`target_slot="all"`, and `_apply_swap` blindly replaced the *last* stop in every slot across the whole trip. **Fix:** added a new `target_stop_name` field to the classifier's schema/prompt, and `_find_stop_by_name()` in `edit_engine.py` to resolve it to the stop's real location (day/slot/position) — exact match first, then an unambiguous-only substring match, then an unambiguous-only category-word match (for "swap **the market**" — a category reference, not a proper name — see next finding). Falls back to the original position-based behavior when the name doesn't resolve, so this only ever narrows scope. **Verified live**: "Swap Humayun's Tomb for Qutab Minar" → *"Swapped: Humayun's Tomb → Qutab Minar."* exactly, no collateral changes; "replace Karim's with another restaurant" → *"Swapped: Karim's → NATRAJ restaurant."*

- **"The market"/"the museum" (a category reference to an existing stop, not its name) fell through to the same broad, wrong-scope behavior.** Real repro: "Instead of the market on day 2, can we do something different?" swapped three unrelated stops across day 2, not the actual market. Same root cause as above, one layer further: the classifier extracted `target_stop_name="the market"`, which correctly found no *name* match — but there was no fallback for a *category* match either. **Fix:** extended `_find_stop_by_name()` to also try resolving a bare category word (after stripping "the"/"a"/"an" and trailing plurals) against real OSM categories, when exactly one scheduled stop anywhere in the trip has that category (unambiguous only, same conservative principle). **Verified live**: now correctly resolves to "Lajpat Nagar Central Market" specifically.

- **A real OSM data-quality artifact surfaced as a swap/add recommendation.** Two genuine records in the POI dataset are literally named **"ME   ♡𓆝"** (decorative symbols + an Egyptian hieroglyph, category "park") — an upstream OpenStreetMap tagging artifact, not a scraping bug — and kept appearing as the top candidate for generic "something different"/"something more fun" swap requests, directly undermining the app's "cited, never invented" credibility with a nonsense result. **Fix:** added `_is_presentable_name()` at `poi_search.py`'s single POI-loading choke point (`_load_pois()`), which every search path shares (initial build, swap, add) — rejects a name only if it contains an astral-plane character (code point ≥ 0x10000 — the block virtually every decorative/emoji/hieroglyph character lives in, while every real script used for Delhi place names — Latin, Devanagari, Perso-Arabic — is entirely within the Basic Multilingual Plane) or has fewer than 3 real letters once whitespace/symbols are stripped. **Verified**: filters exactly 3 of 5,076 real records (the two "ME ♡𓆝" variants plus one Korean word wrongly tagged on a monument); spot-checked against 13 other legitimately Unicode-bearing real names (Karim's, Domino's Pizza, Khair-U'l-Manazil Masjid, etc.) — zero false positives.

- **"Remove the restaurant from day 1 evening" ignored "evening" entirely and could remove the wrong restaurant.** Root cause: `_apply_remove()` never accepted `target_slot` as a parameter at all — it searched *every* slot in the targeted day(s), so a slot-specific remove request could match a same-category/name stop in the wrong slot, which then got correctly caught as scope drift by `check_edit_correctness` one layer up and rolled back — so a well-specified request silently did nothing. **Fix:** added `target_slot` as a real parameter, restricting the search the same way every other edit type already does. **Verified live**: now correctly removes "Nathu Sweets" (the actual evening restaurant) without triggering a rollback.

### Investigated, not a bug

- **Generic trip-level questions (packing, budget, kid-friendliness phrased broadly, "one day instead of two") consistently return the honest no-source decline.** Checked the actual RAG corpus (63 indexed Wikivoyage/Wikidata articles — individual landmark pages plus a few district-level "Delhi" pages): it genuinely has no content on packing lists, trip budgets, or general kid-friendliness ratings as topics. Direct retrieval tests confirm **zero hits** above the relevance threshold for this class of question — the honest decline is correct, not a routing bug; forcing a confident-sounding answer here would mean inventing content the app has no real source for, which is exactly what its whole design exists to prevent. The specific safety-framed and feasibility-framed questions this round's Q-1 fix targets continue to work correctly (verified separately, live, with real grounded content).

**Regression check:** full suite re-run after all five fixes — Phase 2 8/8, Phase 3 8/8 + 4/4, Phase 4 6/6 + guards 5/5, Phase 5 8/8, Phase 6 5/5 — all clean, zero regressions.

**Verification note that shaped the rest of this addendum's process:** the fixes above were first validated with fresh, isolated Python calls (each spins up a new process, so it always imports the latest code from disk) and reported as "fixed and verified." A follow-up request to actually try the app in the browser caught a real gap: the long-running Streamlit **server process** had already imported `edit_engine.py`/`intent_classifier.py`/`poi_search.py` into memory hours earlier, and Python doesn't re-import an already-loaded module just because the file changed on disk — so the live, browser-facing app kept serving the *old, buggy* behavior even after the source fixes landed. The first browser pass reproduced the original bugs exactly. **Restarting the Streamlit server** (not just editing the files) was required before the fixes actually took effect for a real user — confirmed with a second browser pass afterward, all fixes working correctly. Recorded as a durable lesson: after editing code a running server has already imported, restart the server before calling anything "verified."

## Post-Round Addendum 7 — Meal-coverage guarantee over-filled restaurants regardless of stated interest (2026-07-25)

**Trigger:** direct user report — "The application fills in too many restaurants and food options, even when not explicitly called for."

**Root cause, confirmed with real data:** `itinerary_builder.py`'s meal-coverage guarantee (added earlier so a history+architecture trip would never go completely unfed) always targeted **all three** meal slots (breakfast/lunch/dinner) every day, regardless of what the traveler actually asked for — and a second mechanism, the main scheduling loop's budget-reservation logic, pre-emptively set aside room for up to 3 meals (capped at reserving away *half the day's entire budget*) before a single interest-driven stop was even considered. Real repro: an "architecture"-only 3-day trip (zero food/cuisine/eating interest stated) got **3 restaurants out of 5 stops every single day (60%)** — Day 1: `Humayun's Tomb, Purana Qila` (2 real architecture stops) `+ 3 restaurants`.

**Fix:** `itinerary_builder_logic()` now checks whether the caller's own interest-filtered `pois` pool contains any restaurant-category POI at all — since `poi_search.py`'s `INTEREST_MAP` only ever includes "restaurant" when the traveler's stated interests are food/cuisine/eating/dining-related, this is a reliable, already-available signal for "was food actually part of what was asked for," with no need to thread a new parameter through every caller. When food-related interests are absent, the guarantee scales down to **one meal per day** (prioritizing the afternoon/lunch slot — the meal skipping which is most likely to actually inconvenience a full sightseeing day, versus breakfast, usually eaten at the hotel, or dinner, often handled independently) instead of three, and the main loop's budget reservation scales down to match — freeing that budget for the traveler's actual stated interests. Trips that *do* include food-related interests are completely unaffected (still get up to 3 meals/day, unchanged).

**Verified:** direct re-test of the exact repro (architecture-only, 3 days) — every day now has exactly 1 restaurant, with the freed budget going to real additional architecture stops (Day 1 went from 2 architecture stops + 3 restaurants to 3 architecture stops + 1 restaurant). Confirmed food+history trips are unchanged (still 3 restaurants/day). Full regression suite clean (Phase 2 8/8, Phase 3 8/8 + 4/4, Phase 4 6/6, Phase 5 8/8, Phase 6 5/5). **Verified live through the actual browser** (server restarted first): a fresh architecture-only build shows Day 1 with 3 monuments + 1 restaurant, Day 2 with Red Fort, Dilli Haat, one restaurant (Jamun, lunch slot), Qutab Minar — confirmed via screenshot, zero console errors.

**Trigger:** direct question — "Why was Waypoint team not able to identify [these] in their QA reviews?" Rather than just answer, closed the four gaps the answer identified, so future rounds catch this class of bug automatically instead of relying on a user finding them by hand.

**1. **2. Added a booking-vs-cost probe to `phase8_qa/question_commands.py`'s practicalities set (20 → 21).** The original cost probe always used unambiguous wording ("how much does it cost"), so the "ticket" keyword collision (a booking-shaped question getting answered as a cost question) had no way to surface. Added `booking_vs_cost_ambiguity` ("Do I need to book tickets in advance for X?"). Verified: generates correctly.

**3. New `phase8_qa/run_agent_pipeline_sample.py`** — the most structurally important of the four. ## 2. Agent 2 — Edit Command Agent

**Method:** for each of Agent 1's 20 itineraries, 20 edit commands applied **cumulatively** (each builds on the previous, like a real user session) — the original 15 Phase-1 probe types plus 5 new ones this round (whole-trip relax, free-of-charge swap, real-named-place add, same-day reorder, near-gibberish input). Real app code throughout: `phase4/intent_classifier.py` (Gemini) + `phase4/edit_engine.py`, cross-checked with `phase5/edit_correctness.py` (scope-drift detection) and `phase4/feasibility.py` (budget/pacing). Code: `phase8_qa/edit_commands.py`, `phase8_qa/run_edits.py`, `phase8_qa/analyze_edits.py`. Raw output: `phase8_qa/results/edit_itinerary_01.json` .. `edit_itinerary_20.json` (400 commands total).

**Result:** 400/400 commands ran cleanly (396 classified EDIT, 4 EXPLAIN). Edit-type mix: relax 160, swap 116, add 80, remove 20, reduce_travel 20. Full pattern analysis: `phase8_qa/results/_analysis_edits.json`.

### Findings

#### E-1 (HIGH) — "Add a famous local food place" silently breaks travel-time feasibility in 65% of itineraries, with no warning to the user
Confirmed reproducibly in **13 of 20 itineraries** (65%): step 9, "Add one famous local food place to Day 1," succeeds (`ok=True`, itinerary state updated) but always adds the same real venue — **"Local"** — which is 69 minutes of travel from the rest of Day 1's stops, exceeding the app's own 45-minute feasibility threshold. `check_feasibility()` correctly *detects* this (`feasibility_after.pass` flips to `False` with `"travel to Local takes 69 min (> 45 min)"`), but `apply_edit()`'s success message never surfaces it — the user sees only a plain success reply. The break then **persists silently across every subsequent turn** (5+ turns in the traced sessions) until the user happens to separately ask to "reduce travel time between stops" (step 15), which fixes it. A user who doesn't think to ask that unprompted question would carry an infeasible Day 1 for the rest of their planning session without ever being told.
**Evidence:** identical exact pattern (same venue, same 69-min figure, same step 9→15 window) independently reproduced in itineraries 1, 2, 3, 4, 8, 9, 10, 11, 12, 13, 14, 16, 19.
**Fix direction:** `_apply_add` in `phase4/edit_engine.py` should run `check_feasibility()` on the candidate result *before* committing, the same way budget-hour checks already gate other adds (compare to `add_theme_any_day`'s correct budget-based rejections, E-4 below) — and either pick a closer candidate or attach a feasibility warning to the success message rather than staying silent.

#### E-2 (HIGH) — Near-gibberish input is silently classified as "relax" and applied — real stops removed with no clarifying question, 100% of the time
"asldkjf change something idk maybe swap a thing??" — deliberately near-content-free except for the words "change" and "swap" — was classified `edit_type=relax` and **actually applied** (real named stops removed from the itinerary) in **all 20/20 itineraries**, with zero clarifying follow-up. The classifier appears to default to "relax" whenever no clearer edit type is extractable, rather than treating very low lexical confidence as a reason to ask the user what they meant.
**Fix direction:** `phase4/intent_classifier.py` should carry (or `phase3/agent.py` should check) a confidence/ambiguity signal and route sub-threshold inputs to a clarifying question rather than a default guess that mutates the itinerary.

#### E-3 (MEDIUM) — Reorder-within-a-day requests are mishandled 100% of the time, and the majority case returns an actively misleading message
"Swap the order of Day 1's morning and afternoon plans" was never once handled as a reorder: **16/20** were classified `edit_type=swap` (a search for a *replacement stop*, not a reorder) and returned *"Couldn't find a suitable replacement for that swap"* — a message about an entirely different operation than what was asked, since no INTEREST_MAP category is present to search for. The remaining **4/20** were classified `EXPLAIN` instead of `EDIT` at all — an even more fundamental miss. No itinerary reorder capability exists anywhere in `phase4/edit_engine.py`. See also Agent 4's UX3-5 for the UX-layer read on this same gap.
**Fix direction:** either implement a real within-day reorder edit type, or — at minimum — have the classifier recognize "swap the order of X and Y" as a distinct, currently-unsupported request and say so honestly, instead of routing it into the unrelated category-swap search path.

#### E-4 (MEDIUM) — No budget/cost-based constraint support — "something free of charge" fails 100% of the time (but honestly)
"Swap the Day N morning stop for something free of charge" returned *"Couldn't find a suitable replacement for that swap"* in **20/20** itineraries — there is no `INTEREST_MAP` or filter concept for "free"/cost anywhere in the search pipeline, so every such request silently falls through to zero candidates. This is an honest failure (no hallucinated free venue was ever fabricated), which is why it's Medium rather than High — but it's a complete, 100%-reproducible feature gap for a very plausible real request.
**Fix direction:** either add a real cost-aware filter (the dataset does carry `kb_entry_fee` on ~27 POIs per round 4's QA-17 finding, so a "free" filter is at least partially answerable), or have the app say specifically "I can't filter by cost yet" instead of the generic, cost-unaware "couldn't find a replacement" message.

#### E-5 (LOW) — A residual pocket of generic "couldn't find" no-ops, consistent with Phase 1's already-documented pattern
`swap_indoor` (7/20), `swap_theme_category` (4/20), and `remove_real_named_stop` (5/20 — see note below) still occasionally return a generic no-op message. This is the same `SILENT_NOOP` category Phase 1 already identified and only partially addressed; it is **not** a new regression. The `remove_real_named_stop` instances specifically are a harness artifact worth naming rather than hiding: because commands are generated once from the *original* itinerary and applied cumulatively, a stop selected for removal at step 13 may have already been changed by an earlier edit in the same 20-turn session (e.g. "Remove Red Fort from Day 2" when Red Fort was swapped out at step 5) — the app's "couldn't find anything matching" response to that is arguably *correct* (the stop genuinely isn't there anymore), it just doesn't specify *why*, which is exactly what Phase 1's L1 fix (`agent.py`'s `recently_changed_names` transparency message) already addresses **at the conversational-agent layer** — but this harness calls `phase4/edit_engine.apply_edit()` directly, bypassing `agent.py` entirely, so L1's fix isn't exercised here. Flagged for completeness, not as a new defect.

### Things confirmed working correctly (no defect)
- **Zero scope drift** across all 400 edits (`edit_correctness.pass` never failed) — edits stayed contained to their intended day/slot every time.
- **Known-absent-place honesty held 100%** — all 20 "Replace ... with Connaught Place" (swap) and all 20 "Add Select Citywalk mall" (add) requests were correctly and honestly declined, never silently substituted.
- **Invalid day references correctly rejected 20/20** ("Make Day N+2 more relaxed" on an N-day trip).
- **Whole-trip relax correctly touches every day** in all 20 itineraries (`relax_whole_trip` — confirmed via `changed_days`, e.g. a 3-day trip always shows `['day_1','day_2','day_3']`), not just Day 1.
- **Adding a real, itinerary-absent named landmark works correctly and honestly**: "Add Lodhi Garden" succeeded when budget allowed (16/20) and was correctly, *helpfully* declined with a specific reason and an offered alternative ("would push day 2 over the 8.0h budget — I can replace an existing stop instead, or move this to another day") when it didn't (4/20) — genuinely good behavior, not a defect.
- **Themed "add a stop somewhere in the trip" correctly applies real budget-fit logic**, not a bug despite its lower raw success rate (4/20 succeeded outright; the other 16/20 were honest, specific, budget-based declines with a helpful offer, the same good pattern as above).

**Method:** for each of Agent 1's 20 itineraries, 20 probing questions covering Justification, Contingency, Alternatives, Expansion, Practicalities, Suitability, and an edge case — the original 15 Phase-2 probe types plus 5 new ones this round (theme-level justification, immediate-crowd contingency, themed expansion add-on, visit-duration, solo-female-safety suitability). **Result:** 400/400 questions ran cleanly (379 classified EXPLAIN, 21 EDIT/other). 179 grounded / 200 ungrounded-but-honest / 21 not routed to `explain()`. Full pattern analysis: `phase8_qa/results/_analysis_questions.json`.

### Findings

#### Q-1 (HIGH) — The solo-female-safety question is answered with pace-feasibility content, not safety content — and marked "grounded" every time
"Would this itinerary feel safe and manageable for a solo female traveller?" returned essentially the same answer in **all 20/20 itineraries**: *"Yes, this plan looks doable — every day fits within the [pace] budget."* — a response entirely about **schedule feasibility** (whether the hours fit the pace budget), with zero engagement with the actual safety question, and every one of these was tagged `grounded=True`. There is no safety-rating data anywhere in the app's dataset, so a "grounded=True, yes it's safe" answer is actively misleading: a real user asking this question is asking about personal safety, and the app hands back a confident-sounding "yes" sourced from an entirely unrelated field (pace/duration math), not from anything resembling safety information.
**Why this is higher severity than a typical honest-no-source gap:** an honest "I don't have safety data" (as the app correctly gives for several *other* ungrounded probes this round) is the correct failure mode. Here the app doesn't fail honestly — it affirmatively answers "yes, safe" while being *labeled* grounded, which is the one thing this app's whole design philosophy (cited, never-invented data) is built to prevent.
**Fix direction:** `phase4/explain_engine.py` (or its keyword/intent routing) is very likely pattern-matching "manageable" → pace-feasibility lookup while dropping "safe" entirely from the query. This needs its own explicit path: either surface Wikivoyage's actual general safety guidance (already used for the "Getting around Delhi" section elsewhere in the app) for safety-framed questions, or route them to the same honest "no verified source for a per-itinerary safety rating" answer the app correctly gives for other whole-trip-suitability questions — but do not mark a pace-feasibility answer as `grounded` for a safety query.

#### Q-2 (LOW) — "Alternatives to X" is occasionally misclassified as an edit, not a question
2/400 (0.5%) — "What are some alternatives to Karim's on Day 2?" was classified `EDIT` rather than `EXPLAIN` in 2 itineraries, presumably because "alternatives to X" is genuinely ambiguous between "tell me some options" (informational) and "swap it for one" (actionable). Low frequency, but worth noting since it means the question was silently dropped rather than answered.
**Fix direction:** bias the classifier toward `EXPLAIN` for this phrasing unless an explicit action verb ("swap," "replace," "change") is also present.

#### Q-3 (carried over from Phase 2, still present, not new) — Real KB/scheduling data sometimes isn't consulted, falling back to a fresh RAG search instead
8/400 `travel_between_stops` answers didn't draw on the itinerary's own already-computed `travel_time_from_prev_min`/`travel_mode_from_prev` fields for adjacent stops, instead doing an independent text search that came back empty. This is the same `TRAVEL_DATA_AVAILABLE_BUT_UNUSED` pattern Phase 2 already identified (`explain_engine.py` does a fresh RAG lookup by name rather than ever reading the itinerary object's own computed fields) — flagged here only to confirm it's still present at this data scale, not as a new finding.

### Things confirmed working correctly (no defect)
- **Zero uncited claims** — `check_grounding()` never failed across all 400 answers; every answer marked `grounded=True` carried a real citation.
- **Zero false "grounded" denials** — no case where a grounded=True answer actually said "I don't know" in its own text (a mismatch Phase 2 had explicitly checked for).
- **Vague referents correctly clarified 20/20** — "Why did you pick this place?" (no place named) correctly asked "which place are you asking about?" every time, rather than guessing.
- **Honest declines held up at scale**: "Is this itinerary suitable for a family with young kids?" (whole-trip, no single stop) correctly gave an honest no-source answer 20/20; "Is X within walking distance of my hotel?" correctly admitted no lodging data 20/20; "What else can I do on Day N?" correctly gave an honest no-source answer 20/20 rather than inventing filler suggestions.
- **No hallucinated place names found on manual spot-check.** The pattern-analysis script's `POSSIBLE_UNVERIFIED_PLACE_NAME` heuristic flagged 27/400 answers (checking named places only against this app's own internal POI dataset, not a full gazetteer) — but every sampled candidate is a real, verifiable Delhi landmark just outside this app's curated dataset (e.g. "Dina-panah Citadel" — the historical name for Purana Qila; "Hazrat Nizamuddin Dargah"; "National Zoological Park"; "Meherchand Market"; "Dariba Kalan," Chandni Chowk's real silver-market lane). This is a limitation of the analysis heuristic, not evidence of fabrication — worth recording as a **verified-working** result, not a defect.
- **Duration estimates are broadly consistent with the app's own scheduling data.** 8 `duration_named_stop` answers were flagged by the analysis script for an unclear grounding source, but spot-checking them against the itinerary's own assigned `visit_duration_min` (e.g. Humayun's Tomb's app-scheduled 120 minutes vs. the answer's cited "1.5 to 2 hours") found no material inconsistency — the analysis script's own heuristic here was under-specified (it never captured the ground-truth duration value to compare against), a methodology gap in this round's tooling rather than a confirmed app defect.

## 4. Agent 4 — UX Expert Review (benchmarked against Wanderlog)

**Reviewer role:** UX expert, benchmarking specifically against **Wanderlog** (a free AI-assisted day-by-day trip itinerary planner) — the closest functional peer to this app, per the project's own scoping decision for this round. Five prior UX/UI review rounds are already implemented in `QA-UX-Review-and-Recommendations.md` (R-1 through R-34, covering functional bugs, general UX, voice mechanics, a full travel-industry visual benchmark, and voice-first prioritization) — **nothing from those rounds is re-reported here.** This section only reports what a fresh live pass, against the *current* (already-improved) app, actually found.

**Method:** drove the live app at `http://localhost:8501` with Playwright — captured the empty/onboarding state, the build-request → confirm-turn state, the built state (desktop 1280px + mobile 390px), and live post-edit / post-question states, using the same benchmark scenario prior rounds used (2-day food + history trip) for comparability. Screenshots: `scratchpad/r6_screens/r6_01_empty_desktop.png`, `r6_02b_confirm_turn_desktop.png`, `r6_03_built_desktop.png`, `r6_03b_built_map_area.png`, `r6_03c_built_bottom.png`, `r6_04_built_mobile.png`, `r6_05_after_edit_desktop.png`, `r6_06_after_question_desktop.png`.

**Quota note:** this round's live capture spent one real Gemini build + a handful of edit/explain turns (same order of cost as prior rounds' single benchmark build). All six recommendations below are presentation/layout only — **zero** additional LLM/STT calls.

### New UX Findings

#### UX3-1 (HIGH) — The build-confirmation turn is invisible outside the small chat panel
The app doesn't build immediately after a user states their trip — it deliberately asks a yes/no confirmation ("Shall we go ahead and build your itinerary?", the app's real `COLLECT → CLARIFY → CONFIRM → BUILD → PRESENT` state machine, `phase3/agent.py`). But that question surfaces **only** as a chat bubble in the ~1/3-width Transcript column — the dominant 2/3-width "Your Itinerary" panel keeps showing the full, unchanged pre-build onboarding content (hero photo, tagline, capability list, example chips), with zero visual acknowledgment that the agent is waiting on an answer. A user whose attention is on the large left panel — exactly where rounds 4–5 deliberately put all the visual weight — can easily miss it entirely. Confirmed live: `r6_02b_confirm_turn_desktop.png` shows the full onboarding screen completely unchanged while the transcript (only) holds the pending question.
Wanderlog and most AI trip planners don't gate behind an explicit yes/no turn at all — they generate a first-draft plan immediately and let the user refine or regenerate afterward, sidestepping this exact failure mode.
**Fix direction:** surface the pending confirmation in the main panel too — e.g. a highlighted banner with inline Yes/No buttons — not only a chat bubble in the side rail. **Quota impact:** none (the CONFIRM step is existing logic; this is presentation only).

#### UX3-2 (MEDIUM) — The reply audio player is a stray, disconnected element once a plan exists
Live-tested: asking a question after a plan is built (`r6_06_after_question_desktop.png`) renders the "🔊 Speaking your reply…" caption + `st.audio()` player as a full-width strip landing between the map/expanders and the "Email me this plan" section — nowhere near the transcript bubble containing the reply it belongs to. This is the same class of Streamlit column-anchoring bug this codebase has already found and fixed twice (R-27 for the input row; the "Listening Indicator" round for the mic banner): `_play_reply_audio()` runs inside `_send()`, which executes at the top level *after* `col_itinerary, col_side = st.columns(...)` is called but not inside either column's `with` block — so, by the app's own documented anchoring rule, it renders below both columns regardless of where the actual reply text appears.
**Fix direction:** move the audio-playback call inside `col_side`'s transcript block, directly under the reply it accompanies — the exact fix pattern already proven twice in this codebase. **Quota impact:** none.

#### UX3-3 (MEDIUM) — Once a plan exists, the full onboarding-sized input block still pushes the itinerary below the fold
Even after a real 9-stop, 2-day itinerary is built, the entire voice/text input block (mic button, "...or type instead," text field, Send) still renders at full onboarding size above "Your Itinerary" — identical to the empty state (`r6_03_built_desktop.png`). On a 900px-tall viewport the built itinerary's first stop card doesn't appear until well into the page. This is a different problem from round 5's UX-28 (which was about the *pre-build* empty state) — this is the *post-build* state, not previously reviewed. Wanderlog's equivalent (asking its AI to adjust a plan) stays a visually secondary affordance once a plan exists — a compact dock or "Ask AI" entry point — not a full duplicate of its own first-run CTA.
**Fix direction:** compact the input block once `agent.itinerary` is populated (e.g. a single-row "Ask or edit…" field, mic as a smaller icon-button), reserving the large voice-first treatment for the true first-run empty state. **Quota impact:** none.

#### UX3-4 (MEDIUM) — The Transcript panel's fixed height leaves a large dead-space void once scrolled
`st.container(height=480, border=True)` gives the transcript its own internal scroll, but it isn't sticky — once the page is scrolled down to the map, "Getting around Delhi," or the email section, the transcript has long since scrolled out of view, leaving the entire right-hand column blank beside that content (confirmed in `r6_03c_built_bottom.png` — the whole right half of the screen is empty white space past the transcript's 480px). Wanderlog keeps its assistant panel either genuinely sticky or docked so it never strands a full column of unused space.
**Fix direction:** make the transcript column sticky within the viewport, or let the layout reflow to full width once scrolled past it. **Quota impact:** none.

#### UX3-5 (MEDIUM) — No itinerary reordering, and the closest natural-language proxy actively misfires
Wanderlog's signature interaction is drag-and-drop reordering of stops within and across days. This app has no equivalent — and, confirmed live via Agent 2's harness across every sampled itinerary this round, the natural-language proxy for it ("Swap the order of Day 1's morning and afternoon plans") is consistently misclassified as `edit_type=swap` (search-for-a-replacement-stop) rather than recognized as an unsupported reorder request, returning the actively misleading *"Couldn't find a suitable replacement for that swap"* — a message about a different operation than what was actually asked. See Agent 2's `REORDER_MISCLASSIFIED_AS_SWAP` finding for full data.
**Fix direction (UX layer):** if true drag-and-drop is out of scope, give each day's stop list manual up/down move controls as a low-cost substitute. (The classifier-message fix belongs to Agent 2's report.) **Quota impact:** none for manual move controls.

#### UX3-6 (LOW) — No single all-days map; pins aren't interactive beyond a hover tooltip
The per-day pydeck map (numbered pins, route line) is a solid, honest, real-data visualization — but it only ever shows one day at a time, and pins don't do anything beyond a name tooltip (no jump-to-stop). Wanderlog's map is its anchor screen: all stops across all days at once, day toggled by color/filter, with pins that jump the list to that stop. Given this project's documented no-mapping-SaaS-budget, local-only constraint, this is a lower-priority polish item, not a core gap — and a true click-to-jump isn't free: Streamlit's pydeck wrapper has no Python-side click callback, so the realistic substitute is a day-toggle multiselect plus a stop `selectbox`, not a literal map click.
**Quota impact:** none.

### Things already matching or exceeding Wanderlog-caliber UX (verified, no action needed)
- **Grounded-data trust signaling** (fee/hours badges, the green "Real data" badge) — arguably stronger honesty than Wanderlog, which blends in unverified user-submitted listings.
- **Voice-first flow** (mic as the dominant CTA, idle pulse, live Listening/Transcribing banners) — Wanderlog has no comparable voice-input capability at all; a genuine differentiator, confirmed still working cleanly this round.
- **Card-based, photo-backed stop layout with a real clock-time timeline** — on par with Wanderlog's day view, holds up under fresh live inspection.
- **Honest "I don't have a verified source" answers** rather than fabricated specifics — repeatedly observed in this round's Agent 3 run; Wanderlog, backed by Google Places/user data, doesn't need this discipline, but for a grounded-data product it's a real strength, not just an absence of gaps.

## 5. Agent 5 — UI Expert Review (benchmarked against Wanderlog)

**Reviewer role:** visual/interaction design specialist — same live-driven method as Agent 4, but focused on the visual *system* (color, type, imagery, iconography, spacing) rather than flow/information-architecture (Agent 4's lens). Builds on rounds 4–5's card/photo/badge/theme work (R-22 through R-34); only reports what's still open or newly observed.

### New UI Findings

#### UI3-1 (MEDIUM) — No real type scale; brand title and section headers share the same visual weight
`phase6/.streamlit/config.toml`'s `[theme]` block sets only `primaryColor = "#C2540C"` — no `font`, no deliberate heading scale. Live screenshots show "🧭 Delhi Travel Planner" (page title), "Your Itinerary," and "Transcript" (both section headers) all in the same default sans-serif, differentiated only by the raw HTML heading level Streamlit assigns — no deliberate size/weight/color distinguishes the brand identity from a plain content header. (Round 4's R-26 explicitly implemented the accent color + hero image but never claimed a type scale — this is a legitimately still-open gap, not a broken promise.)
Wanderlog benchmark: a distinct, heavier display face for trip titles vs. a lighter, smaller UI font for body/metadata — an immediate hierarchy cue this app lacks.
**Fix direction:** add a `[theme] font=` choice (Streamlit supports named Google Fonts) and/or custom CSS giving the page title a larger/bolder treatment distinct from `st.subheader()` calls. **Quota impact:** none.

#### UI3-2 (MEDIUM) — Photo/no-photo stop cards create an uneven, patchy grid
Cards for stops with a real Wikidata photo (Humayun's Tomb) sit directly beside cards with a flat gray placeholder box + small category emoji (Karim's, Indian Accent, Khan Market — confirmed in `r6_03_built_desktop.png` / `r6_03b_built_map_area.png`). Both card types are structurally identical, so the inconsistency reads as "half-finished" rather than "some venues don't have public photos" (a fact of the underlying open data — restaurants rarely carry Wikidata P18 images the way monuments do; round 4's QA-17 found 75 landmark photos in the dataset, and almost none are meal stops).
**Fix direction:** give the placeholder a more deliberate, branded treatment (a subtle gradient in the theme's accent color, or a muted generic texture) instead of flat mid-gray, so it reads as "on-brand illustration" rather than "missing image." **Quota impact:** none (static asset only).

#### UI3-3 (LOW) — The accent system is one hue applied inconsistently; badges/markers default to unrelated colors
Only one deliberate brand color exists (`#C2540C` terracotta — primary button, active tab). Everything else uses component-default colors unrelated to it: the fee badge is Streamlit's stock green, the hours badge is stock blue, and the day-map markers use a third palette (orange/blue/purple for morning/afternoon/evening, chosen for semantic distinction, not brand fit). The result is four-plus unrelated hues on one screen with no unifying system. Wanderlog uses a cohesive blue/teal family throughout, reserving a distinct accent only for true calls-to-action.
**Fix direction:** not a call to flatten the semantic color-coding (fee/hours/time-of-day distinctions are genuinely useful) — re-derive those accents as tints/shades of the existing terracotta plus one deliberately chosen complement, instead of Streamlit's arbitrary stock badge colors. **Quota impact:** none.

#### UI3-4 (LOW) — Map markers are generic colored dots with no category iconography
The pydeck `ScatterplotLayer` renders plain colored circles with a number — functional and honest, but generic next to Wanderlog's category-coded pin icons (fork for restaurants, monument glyph for landmarks) that let a user read the map without hovering. The app already has the glyphs it needs (the `CATEGORY_ICON` dict used for photo-less stop cards) — the map layer just doesn't reuse them.
**Fix direction:** pydeck's `IconLayer` can render a small category glyph per point, reusing `CATEGORY_ICON` — though `IconLayer` needs image URLs rather than emoji text, so this requires a modest one-time asset-generation step, not a one-line change. **Quota impact:** none (one-time asset generation, no LLM calls).

#### UI3-5 (LOW) — The onboarding hero photo is one specific monument, not a destination-level image
The empty-state hero is a single real Red Fort photo (R-26's fix) shown regardless of what the user is about to plan — a food-only or nature-only trip still opens on a monument photo, slightly overpromising a specific site before any preference is known. Given this project's documented no-stock-photo-budget constraint, a genuinely destination-neutral alternative may not exist in the same license-clean Wikidata pipeline — flagged as a minor, only-if-cheap observation, not a strong recommendation. **Quota impact:** none if a suitable alternate Wikidata image exists; otherwise not worth pursuing.

### Things already matching or exceeding Wanderlog-caliber visual design (verified, no action needed)
- **Real photography on landmark cards** (round 4's flagship fix) — genuinely competitive with any product in this class.
- **Consistent card-grid rhythm, colored fact badges, real clock-time timeline** — R-23/R-24/R-25 hold up well under fresh live inspection.
- **De-prototyped shell** — zero visible Streamlit "Deploy"/hamburger chrome in any screenshot this round.
- **Responsive mobile layout** (390px) — cards reflow cleanly, no horizontal scroll, no broken elements (`r6_04_built_mobile.png`).

## 7. Summary

This round ran **1,200 real, non-mocked interactions** against 20 freshly generated itineraries — 400 edit commands, 400 probing questions, plus a live Playwright-driven design walkthrough — and found **three High-priority, 100%-or-majority-reproducible defects** that hadn't surfaced in Phase 1/2's QA (which used a different, hand-curated itinerary batch and a different, smaller command set):

1. **A specific "add famous food" edit silently breaks travel-time feasibility in 65% of itineraries** with no warning, persisting for multiple turns until the user happens to separately ask to reduce travel time.
2. **Near-gibberish input is silently interpreted as an edit and applied 100% of the time**, removing real itinerary content without ever asking the user to clarify.
3. **A safety-framed question gets a confidently "grounded" answer built from unrelated pace-feasibility data**, 100% of the time — the one failure mode this app's cited-data design philosophy is specifically meant to prevent.

Against that, the round also **positively confirmed** a large amount of correct, honest behavior at real scale: zero scope drift across 400 edits, zero uncited claims across 400 questions, 100% honest handling of known-absent places / invalid days / vague referents / missing-context questions, and — on manual spot-check — zero actual place-name hallucinations despite a heuristic flag suggesting otherwise. The app's core "cited, never invented" discipline holds up well under a much larger and more adversarial load than it had previously been tested with; the gaps found are specific, fixable logic gaps (missing a feasibility re-check on one edit path, an overeager low-confidence default, one mismatched question-routing case), not a systemic honesty problem.

On the design side, benchmarked specifically against **Wanderlog**: the app's five prior UX/UI rounds (R-1–R-34) hold up well under fresh live inspection — real photography, card-based stops, a real clock-time timeline, a de-prototyped shell, and a genuinely differentiated voice-first flow all still work as documented. The six new UX findings and five new UI findings this round are largely about **post-build state** (an area the prior rounds' benchmark scenarios didn't focus on as closely as the empty/onboarding state) — a confirmation step that's easy to miss, screen real-estate that doesn't rebalance once a plan exists, and a visual system (type scale, color cohesion) that's still one deliberate accent color short of feeling like a fully branded product rather than a very polished prototype.

**Bottom line:** no regressions found in previously-fixed areas; three new, well-evidenced High-priority findings worth fixing before the next round; a clear, prioritized UX/UI punch list benchmarked against a named competitor as requested.
