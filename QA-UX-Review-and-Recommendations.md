## 1. Summary

The app is in **good, demo-ready shape**. A full multi-turn conversation ("Plan a 2-day trip to Delhi, I like food and history, moderate pace, 2 people" → "Yes, build it") successfully produced a real, grounded 2-day itinerary with day tabs, per-stop categories/durations/opening hours/meal labels, a hidden-gem badge (💎), travel time + mode icons, official-site links, per-day emergency info (hospital/pharmacy/metro with distances), a live map with stop markers, a "Getting around Delhi" transit expander, and a rich "Full Itinerary" narrator (Trip Overview → Food Highlights → Getting Around → Budget Estimate → Practical Tips, with sensible "estimated — verify locally" caveats). **One high-severity gap stands out:** LLM calls have **no rate-limit / error handling**, so when the shared Groq quota is exhausted mid-conversation the OpenAI-compatible SDK raises an uncaught `RateLimitError` (HTTP 429) that propagates all the way into the Streamlit script and renders a full traceback in the UI. This matches the previously reported behavior and is confirmed to still be present in the current code.

**Testing limitations (could NOT verify):**
- **Real speech recognition accuracy and TTS audio quality** — require a human with a microphone and speakers. I verified only that the buttons engage and do not crash.
- **Actual email delivery** — SMTP is intentionally unconfigured in `.env`, so I exercised only the (correct) graceful fallback path. I used the reserved, non-deliverable `example.com` domain for the valid-email test to avoid sending any real mail.
- **Groq quota budget used:** one full build + one edit + one explain (the minimum needed to cover the required surface). All downstream feature tests reused that single built itinerary in one browser session rather than rebuilding, to conserve the shared 100k-token daily quota.

## 2. QA Findings

### QA-1 (HIGH) — Unhandled Groq quota / rate-limit error crashes the running app
- **What's broken:** `TravelAgent._llm()` (`phase3/agent.py:124-131`) calls `client.chat.completions.create(...)` with no `try/except`, and `app.py:59` / `app.py:69` call `agent.process_turn(...)` with no guard. The client is the OpenAI SDK pointed at Groq's base URL (`config.py:22-29`), so an exhausted daily quota raises `openai.RateLimitError` (429). Nothing catches it, so it bubbles into the Streamlit script run and the UI shows a red "This app has encountered an error" traceback. The same is true of `EnvironmentError` from `get_llm_client()` if `GROQ_API_KEY` is ever missing.
- **Repro:** Exhaust the Groq daily token quota, then send any message that triggers an LLM call (agent decision, build, edit, or explain). *(Confirmed by code inspection rather than by deliberately burning the shared quota.)*
- **Severity:** High — it's the single most likely failure in a live demo, given the project has repeatedly hit this exact limit, and it presents to the user as a raw stack trace rather than a graceful message.
- **Evidence:** `phase3/agent.py:124-131`, `phase6/app.py:57-70`, `config.py:22-29`.

### QA-2 (MEDIUM) — Edits don't refresh the narrative/enrichment, so the "Full Itinerary" overview goes stale
- **What's broken:** In `_handle_post_build_turn` (`phase3/agent.py:419-457`) an `EDIT` updates `self.itinerary` (with correctness + feasibility guardrails), but never re-runs `_generate_narrative()` or the weather/safety/transit enrichment — those are only produced during the initial `_build_itinerary()` (`agent.py:266-268`). After "Make day 1 more relaxed," the Day tabs reflect the new plan while the "📖 Full Itinerary" expander and the per-day emergency-info line still describe the *pre-edit* itinerary. A user reading the overview can get an inconsistent picture.
- **Repro:** Build an itinerary → open "Full Itinerary" and note the Day 1 description → send "Make day 1 more relaxed" → the day tab changes but the narrative overview does not.
- **Severity:** Medium — no crash, but a correctness/consistency issue that undermines trust in the grounded plan.
- **Evidence:** `phase3/agent.py:419-457` vs `phase3/agent.py:246-295`.

### QA-3 (MEDIUM) — Mic button freezes the whole app and can silently spend Groq quota
- **What's broken:** Clicking "🎤 Speak" runs `try_listen_via_mic()` → `STT.listen()` server-side, which calls `recognizer.listen(source, timeout=10, phrase_time_limit=15)` and then sends the captured audio to **Groq Whisper** for transcription (`phase3/stt.py:46-84`). Because Streamlit is single-threaded, the entire UI is frozen on a "Listening..." spinner for up to ~10–25s with no cancel affordance. On a machine that *has* a microphone (as here — the button engaged and stayed in "Listening..."), an accidental click records ambient audio and spends Groq Whisper tokens even though the user never intended to speak. The graceful "I didn't catch that / Microphone unavailable" fallback only appears *after* the timeout.
- **Repro:** Click "🎤 Speak" and don't speak → the app blocks on "Listening..." for the full timeout before recovering.
- **Severity:** Medium — no crash, but a frozen UI plus an unadvertised quota cost.
- **Evidence:** screenshot `11_mic.png` (stuck on "Listening..."), `phase3/stt.py:46-84`, `phase6/voice_input.py`.

### QA-4 (LOW) — Email fallback message leaks internal configuration to end users
- **What's broken:** When SMTP is unset, the user sees: *"Saved your itinerary locally (…docx). Email wasn't sent: SMTP not configured — set SMTP_HOST, SMTP_USER, SMTP_PASSWORD in .env."* (`phase6/delivery.py:61`, `phase6/email_sender.py:31`). Naming `.env` variables is developer language, not something a traveler should see.
- **Repro:** With SMTP unset, enter a valid email and click "Send itinerary."
- **Severity:** Low — cosmetic/professionalism; the functional fallback (local save + working download) is correct.
- **Evidence:** screenshot `09_email_valid.png`.

### QA-5 (LOW) — Log flooded with `torchvision` tracebacks from Streamlit's file watcher
- **What's broken:** `streamlit.log` repeats dozens of `ModuleNotFoundError: No module named 'torchvision'` tracebacks. These come from Streamlit's local-sources file watcher walking `transformers` module paths — **not** an app runtime crash. But the noise makes the log nearly useless for spotting real errors (e.g., it could easily bury a genuine `RateLimitError`).
- **Repro:** Start the app and inspect `phase6/streamlit.log`.
- **Severity:** Low — operational hygiene, not user-facing.
- **Evidence:** `phase6/streamlit.log` (lines ~1990–2495).

### Things verified working (no defect)
Text input + Send; multi-turn extract → confirm → build; 2 Day tabs; scheduled-time caption; emergency info; per-stop category/duration/opening-hours/meal/💎-badge/travel-mode/official-site link; map markers; "Getting around Delhi" expander; "Full Itinerary" narrator (non-empty, well formatted); Sources panel after an explain; edit accepted without crash; invalid-email rejection ("that doesn't look like a valid email address"); valid-email graceful fallback + working `.docx` download (valid 39 KB, 77 paragraphs); voice-output checkbox toggle; "Start a new trip" reset (itinerary + transcript cleared); empty-submission guard (`app.py:57`, `and user_text.strip()`); attribution footer present and correct. ## 3. UX Observations

- **UX-1 — No build wait-state feedback.** The build takes ~15–30s (POI search + itinerary build + evals + enrichment + the large narrator prompt). During that time the itinerary panel just keeps showing the "Tell me about your trip to get started" placeholder, and the only progress cue is Streamlit's tiny top-right "Running" spinner. A first-time user has no idea whether anything is happening. (Screenshot `03_itinerary_built.png` was captured mid-build and shows the still-empty panel.)
- **UX-2 — Map markers are unlabeled and unordered.** `st.map(..., zoom=10)` plots all stops as identical red dots with no numbering or day/route association, so users can't tell which dot is which stop or the order to visit. (`05_day_tabs.png`)
- **UX-3 — Content redundancy between the structured panel and the narrator.** The emergency info and safety tip appear both in the day panel/enrichment and again inside the "Full Itinerary" narrative, lengthening an already long page.
- **UX-4 — Transcript is a flat bold-label list.** Long agent turns (build summary + weather + multi-sentence safety tip) make the right column very tall with no chat-bubble grouping or visual separation between "You" and "Agent." (`05_day_tabs.png`)
- **UX-5 — Weak citation labels.** The Sources panel shows a single link literally titled "Delhi" (the Wikivoyage page), which gives low information scent about *what* was cited. (`07_after_explain.png`)
- **UX-6 — Jargon in labels/messages.** "🔊 Speak responses aloud (server audio)" ("server audio" is developer framing) and the SMTP fallback message (QA-4) read as internal language.
- **UX-7 — Input row spacing.** The form uses columns `[1, 1, 6]`, leaving a large empty gap to the right of "🎤 Speak"; Send and Speak sit close together with the mic slightly detached, which reads as slightly unfinished. (`01_initial.png`)
- **UX-8 — Accessibility basics.** Meaning is sometimes carried by emoji alone (🏥 💊 🚇 💎); the map has no text alternative; and the gray `st.caption` text (scheduled time, emergency line) is low-contrast. Most icons are paired with text, so this is minor but worth a pass.
- **UX-9 — Mobile (~400px) behaves well.** The two-column layout stacks into a clean single column, the sidebar collapses to a "»" control, and the narrator markdown renders cleanly — good responsive behavior. The main cost is a lot of vertical scrolling past the map and long narrative. (`10_mobile.png`)
- **UX-10 — Positive: grounding and honesty are visible.** Real opening hours, real distances, official-site links, and "estimated — verify locally" budget caveats all signal trustworthiness and are a genuine strength of the experience. (`04`, `05`, `10`)

## 4. Recommendations

Each item notes **Groq quota impact** explicitly. Given the shared 100k-token/day free-tier limit that this project repeatedly exhausts, quota-neutral and quota-*reducing* fixes are favored, and any recommendation that would add LLM calls is flagged and weighed.

### High priority

**R-1. ✅ IMPLEMENTED (2026-07-13). Wrap all LLM calls in graceful error handling (fixes QA-1).**
Catch `RateLimitError` (and a generic fallback) around `_llm()` in `phase3/agent.py` and/or around `agent.process_turn(...)` in `app.py`, and surface a friendly message such as *"We've hit today's AI usage limit — please try again later. Your itinerary so far is preserved."* Also catch the `EnvironmentError` from `get_llm_client()` for a missing key.
**Groq quota impact: NONE (and defensively valuable).** This adds zero LLM calls — it's pure exception handling. It is *especially* worth doing precisely because the quota gets hit: it turns the app's most likely failure from a raw traceback into graceful degradation. Top priority.
*Implementation:* `TravelAgent.process_turn()` now wraps its body (moved to `_process_turn_inner()`) in a try/except that catches `openai.RateLimitError`, `openai.AuthenticationError`/`EnvironmentError`, `openai.APIError`, and a generic fallback — each with a distinct friendly message via `_handle_turn_failure()`, which also logs a synthetic assistant turn so conversation history stays coherent. Verified with a real `openai.RateLimitError` instance (proper `httpx.Response`-backed mock, not a real quota burn): agent returns the correct friendly message and preserves state instead of raising.

**R-2. ✅ IMPLEMENTED (2026-07-13). Add explicit build wait-state feedback (fixes UX-1).**
Wrap the build turn in `st.status("Building your itinerary — finding real places, checking feasibility… (~30s)")` or a spinner over the itinerary column so users know the 15–30s wait is expected.
**Groq quota impact: NONE.** UI-only; no extra model calls.
*Implementation:* both `app.py` message-send and mic-send paths now wrap `agent.process_turn(...)` in `st.spinner("Thinking... (building a full itinerary can take up to 30s — searching real places and checking feasibility)")`. Verified live in the browser — the spinner text renders during the build wait.

### Medium priority

**R-3. ✅ IMPLEMENTED (2026-07-13). Keep the narrative consistent with edits (fixes QA-2).**
Preferred (quota-neutral) approach: after an edit, either **clear** the now-stale narrative/enrichment or **label** the "Full Itinerary" expander as *"Overview of your original plan — the Day tabs above reflect your latest edits."* so users aren't misled.
**Groq quota impact: NONE for the label/clear approach.** The alternative — **regenerating the narrator on every edit** — would add a large 1,500–2,500-token LLM call per edit and is **quota-risky; deprioritize it.** Recommend the label/clear option, which achieves consistency at zero token cost.
*Implementation:* went with the label approach. Added `TravelAgent.narrative_stale: bool` (init'd `False`, reset on `reset()`), set `True` only when a real edit commits (`self.itinerary = outcome["itinerary"]` in `_handle_post_build_turn`'s EDIT branch — correctly *not* set when an edit is rejected by the correctness/feasibility guard), and cleared back to `False` whenever `_generate_narrative()` succeeds. `phase6/app.py`'s "Full Itinerary" expander shows a caption warning when stale. Verified live end-to-end: no warning before any edit, warning correctly appears after a real committed edit ("Made it more relaxed — removed Shanker's International Doll Museum to free up time"), and the narrator's own content (which references the pre-edit stop) is left as-is rather than silently going wrong — the label makes the staleness explicit instead of hiding it.

**R-4. ✅ IMPLEMENTED (2026-07-13). Make the mic safer and non-surprising (mitigates QA-3).**
Set a clear expectation on the "Listening…" state (e.g., "Listening for up to 10 seconds…"), shorten the STT `timeout`, and/or gate transcription so an accidental click doesn't silently record and transcribe.
**Groq quota impact: mic transcription itself ADDS Groq Whisper calls — but this recommendation *reduces* that risk** (shorter listen window, explicit intent), so it is net quota-positive. Worth doing.
*Implementation:* `phase3/stt.py`'s `_from_mic()` timeouts reduced from `timeout=10, phrase_time_limit=15` (worst case ~25s) to `timeout=5, phrase_time_limit=10` (worst case ~15s), cutting both the UI freeze and the amount of ambient audio an accidental click can send to Groq Whisper. `app.py`'s mic spinner text updated to state the new bounds explicitly ("Listening... (up to 5s to start speaking, up to 10s of speech)"). Real speech-accuracy impact not independently re-verified (same testing limitation as the original review — needs a human with a microphone).

### Low priority

**R-5. ✅ IMPLEMENTED (2026-07-13). User-friendly email fallback copy (fixes QA-4).** Replace the SMTP-env-var text with something like *"We couldn't email it right now, but your itinerary is saved — download it below."* **Groq quota impact: NONE.**
*Implementation:* `phase6/delivery.py` no longer echoes `email_sender.py`'s developer-facing `reason` string (which could be raw SMTP config hints or a raw `smtplib` exception) into the user-visible message — it's now logged server-side (`print(f"  [delivery] email send failed: {result['reason']}")`) and the user sees a generic "We couldn't email it right now, but your itinerary is saved — download it below (…)". `test_phase6.py`'s T-6.4 assertion updated to check for the new copy and confirm "SMTP" never appears in the user-facing message. Verified: 5/5 Phase 6 tests pass.

**R-6. ✅ IMPLEMENTED (2026-07-13). Silence the file-watcher noise (fixes QA-5).** Set `server.fileWatcherType = "poll"` (or exclude `transformers`) in Streamlit config so `torchvision` import tracebacks stop flooding the log and can't bury a real `RateLimitError`. **Groq quota impact: NONE.**
*Implementation:* new `phase6/.streamlit/config.toml` sets `[server] fileWatcherType = "poll"` — switches from watchdog's import-introspection-based watcher (which walks `transformers`' optional `torchvision` import and logs a `ModuleNotFoundError` every check) to plain mtime polling.

**R-7. ✅ IMPLEMENTED (2026-07-13). Number/label map markers by stop and (ideally) day (fixes UX-2).** Render numbered markers or a per-day route so dots map to stops. **Groq quota impact: NONE** (client-side rendering from existing lat/lon data).

A caption below the map spells out the color/number legend as a text alternative (doubles as R-10's map alt-text). Verified live via Playwright: numbered, color-coded markers with a connecting route line render correctly, no console errors.

**R-8. ✅ IMPLEMENTED (2026-07-13). Strengthen citation labels (fixes UX-5).** Show the section/topic alongside the source (e.g., "Delhi — Stay safe (Wikivoyage)") instead of a bare "Delhi." **Groq quota impact: NONE** (the citation metadata already exists; this is presentation only — do *not* add an LLM summarization pass, which would cost tokens).

### New QA Findings

#### QA-6 (HIGH) — The same POI is scheduled twice in one day, under two different spellings
- **What's broken:** A built 2-day itinerary places **"Shanker's International Doll Museum"** in Day 1 Morning *and* **"Shankar's Doll Museum"** in Day 1 Afternoon — the same museum, visited twice on the same day, with two inconsistent name spellings. It appears this way in the structured day panel, is repeated in the "Full Itinerary" narrator (which even writes *"Visit the doll museum again to explore more exhibits"*), and is echoed in the spoken summary (*"Day 1 starts at Shanker's International Doll Museum…"*). The itinerary builder is treating two records of one place as distinct POIs and the grounding eval doesn't catch it (both spellings are "grounded"; it only checks membership, not intra-day duplication).
- **Repro:** Build a 2-day food+history itinerary; open Day 1. Confirmed in `qa-review\r5_r10_verification.png` and in `downloaded.docx` Day 1.
- **Severity:** High — this is the trust-differentiator ("real, grounded places, no hallucination") visibly failing: a duplicate/redundant stop is exactly what a careful traveler will notice first, and it makes the plan look machine-generated and unreviewed.
- **Evidence:** `qa-review\r5_r10_verification.png`; `qa-review\downloaded.docx` (Day 1 bullets); dedup would live in the Phase 2 itinerary builder / a post-build eval.

#### QA-7 (MEDIUM) — Out-of-scope keyword filter derails an in-progress Delhi conversation
- **What's broken:** `_is_out_of_scope()` (`phase3/agent.py:571-584`) runs on **every** pre-build turn (`agent.py:204`) and does a bare **substring** match against a hardcoded city list. It rejects the turn unless the literal word "delhi" appears **in that same message**. So mid-planning, a user who says *"Actually I love street food like they have in Mumbai"* — a comparison, not a request to plan a Mumbai trip — gets the hard bounce *"I specialize exclusively in New Delhi travel planning…"*, losing their turn even though Delhi context was established earlier. Confirmed live this session (rejection fired as designed). Substring matching is also fragile (e.g. "goa" inside other tokens) and the check silently discards whatever real preference the user was expressing in that message.
- **Repro:** Start a Delhi plan; on a later turn mention another city as an aside without repeating "delhi". Agent rejects the whole turn.
- **Severity:** Medium — no crash, but it's a genuine conversational-flow failure: the agent feels brittle and "deaf" to context exactly when the user is trying to add nuance.
- **Evidence:** `phase3/agent.py:571-584`, `agent.py:204-209`; `qa-review-phase2\p2_02_oos_derail.png`.

#### QA-8 (MEDIUM) — Narrative/safety/transit enrichment fails *silently* under a rate-limited build
- **What's broken:** `_run_post_build_enrichment()` and `_generate_narrative()` (`phase3/agent.py:305-382`) wrap the weather note, the safety RAG tip, the transit RAG panel, and the whole "Full Itinerary" narrator in best-effort `try/except: pass` blocks. ### New QA Findings (voice)

#### QA-10 (MEDIUM) — Long spoken input is silently truncated at 10 seconds
- **What's wrong:** `_from_mic()` captures with `recognizer.listen(source, timeout=5, phrase_time_limit=10)` (`phase3/stt.py:62`). `phrase_time_limit=10` hard-caps a single utterance at 10s — a traveler giving a natural, detailed request ("I've got three days, I love Mughal history and street food, but I want a relaxed pace and my parents are with me so…") is **cut off at 10s**, and only that first slice is transcribed and sent to the agent. Nothing tells the user their sentence was clipped.
- **Why it matters:** Voice users speak in longer, less-structured bursts than they type; silent truncation drops exactly the constraints (pace, group, dietary) the planner depends on, and the user can't see why the plan ignored half of what they said.
- **Fix:** See R-20 — raise/relax the cap with an explicit max, or detect truncation and surface "I only caught the first bit — want to add more?".
- **Quota impact:** none (capture-side setting). **Evidence:** `phase3/stt.py:62`.

#### QA-11 (MEDIUM) — Every STT failure mode collapses into one identical "I didn't catch that" message
- **What's wrong:** Three very different failures return the **same** empty string and therefore the **same** user message. Verified by injecting stubs through `try_listen_via_mic()`:
  - Silence / no speech in time (`WaitTimeoutError` → `""`, `stt.py:63-64`) → *"I didn't catch that. Please try again or use the text box instead."*
  - A **Groq Whisper API failure / rate-limit / network error** during transcription is swallowed inside `_from_mic` (`except Exception: … return ""`, `stt.py:71-73`) → **the exact same** *"I didn't catch that…"* message.
  So a user whose transcription failed because Groq is down or rate-limited is told they didn't speak clearly — they'll keep re-recording (spending more Whisper quota) instead of being told to wait or type.
- **Why it matters:** The remedy differs per cause (speak again vs. wait/retry later vs. type), but the app gives one undifferentiated instruction, so users take the wrong recovery action.
- **Fix:** See R-18 — distinguish "no speech" from "transcription service error" and surface cause-appropriate guidance.
- **Quota impact:** *reducing* — clearer messaging avoids repeat Whisper calls on a service outage. **Evidence:** `phase3/stt.py:66-89`, `phase6/voice_input.py:29-30`; confirmed via fake-factory injection (silence and swallowed-Groq-error both produced the identical string).

#### QA-12 (LOW) — Raw mic/hardware exception text is leaked into the user-facing message
- **What's wrong:** `try_listen_via_mic()` interpolates the raw exception into the UI string: *"Microphone unavailable (`{e}`). Please use the text box instead."* (`phase6/voice_input.py:33`). Verified injection produced *"Microphone unavailable ([Errno -9996] Invalid input device (no default output device available)). Please use the text box instead."* — a cryptic PortAudio/PyAudio errno shown to a traveler. This is the same class of leak as the already-fixed QA-4 (email) and QA-9 (raw OSM tokens), but on the mic path.
- **Why it matters:** Developer-level error strings read as broken/unpolished and mean nothing to an end user.
- **Fix:** See R-18 — friendly fixed copy; log the technical detail server-side only.
- **Quota impact:** none. **Evidence:** `phase6/voice_input.py:32-33`; verified via injected `OSError`.

#### QA-13 (HIGH) — "Read replies aloud" playback fully blocks the UI for the whole spoken duration, with no way to stop it
- **What's wrong:** `TTS._speak_edge()` busy-waits until audio finishes — `while pygame.mixer.music.get_busy(): pygame.time.Clock().tick(10)` (`phase3/tts.py:78-79`). That call sits inside `agent.process_turn()` (via `agent._say()`), which `app.py` runs **synchronously inside the `st.spinner(THINKING_MESSAGE)`** block (`app.py:88-89`). So with the toggle on, every turn holds the single Streamlit thread — and the whole UI — frozen on "Thinking…" until playback **completely finishes**. A build turn speaks *two* segments (the "Great! Let me search…" line and then the full spoken summary, which includes the multi-sentence weather + **safety** monologue), so the app can be locked for 30–60s+ per build. There is **no Stop/skip control and no barge-in** — the user cannot interrupt the agent or start their next turn until the voice finishes.
- **Why it matters:** This is the central defect of a *voice-first* app: enabling the headline voice feature makes the product feel hung, and forces the user to sit through a long, unstoppable safety monologue every build. The architecture doc already acknowledges true interruptibility was deferred (Pipecat/LiveKit "options considered but not built") — but even without that rewrite, the *blocking* and the *missing stop button* are fixable.
- **Fix:** See R-17.
- **Quota impact:** none (playback/threading). **Evidence:** `phase3/tts.py:74-82`, `phase6/app.py:86-89`; `phase3/agent.py` `_say()` calls are synchronous within `process_turn`. *Live human verification still needed* for exact playback durations.

#### QA-14 (MEDIUM) — Fallback to the robotic offline voice is invisible to the user
- **What's wrong:** When edge-tts fails (e.g. no network), `speak()` catches it and prints *"edge-tts unavailable (…) — falling back to offline voice"* to the **server console only** (`phase3/tts.py:57-59`), then plays via pyttsx3. Verified by monkeypatching `_speak_edge` to raise: the pyttsx3 path is invoked and the notice goes to stdout, **nothing reaches the browser**. The user just suddenly hears a markedly more robotic voice with zero on-screen explanation.
- **Why it matters:** An unexplained voice-quality drop reads as a glitch; a one-line UI note ("using offline voice — reconnect for the natural voice") turns a mystery into an understood degradation.
- **Fix:** See R-19.
- **Quota impact:** none. **Evidence:** `phase3/tts.py:55-59`; verified via fallback stub (console-only notice, pyttsx3 invoked).

#### QA-15 (MEDIUM) — The pyttsx3 fallback reuses a cached global engine and may hang/go silent on the 2nd+ reply
- **What's wrong:** `_get_pyttsx3_engine()` caches one engine in a module global (`phase3/tts.py:29-36`) and `_speak_pyttsx3()` calls `engine.say(text); engine.runAndWait()` on **every** turn (`tts.py:84-88`). Reusing a single persisted pyttsx3 engine across repeated `runAndWait()` calls is a well-documented failure mode (especially on Windows SAPI5): the first utterance works, later calls can hang or return without speaking. Because the fallback only triggers when edge-tts is already down (offline), the user in that exact situation is most likely to get a silent or frozen second reply.
- **Why it matters:** The fallback exists precisely for the degraded/offline case; if it only reliably speaks once, it doesn't actually provide resilient voice.
- **Fix:** See R-19 (re-init per call or otherwise avoid the persisted-engine `runAndWait` pattern).
- **Quota impact:** none. **Evidence:** `phase3/tts.py:29-36, 84-88`. *Live human verification still needed* to confirm the hang on this specific SAPI5 stack.

#### QA-16 (LOW) — Temp `.mp3` files leak when playback errors mid-way
- **What's wrong:** `_speak_edge()` creates a temp mp3 via `mkstemp` and only deletes it with `os.remove(path)` on the **success path after** the busy-wait (`phase3/tts.py:65-82`). If `pygame.mixer.music.load/play` raises (corrupt file, mixer init issue), the exception propagates to `speak()`'s `except` (→ pyttsx3 fallback) and the temp file is **orphaned** in the system temp dir. Repeated failures accumulate files.
- **Why it matters:** Minor hygiene, but unbounded temp growth over a long-running demo session.
- **Fix:** See R-21 (`try/finally` cleanup).
- **Quota impact:** none. **Evidence:** `phase3/tts.py:65-82`.

### New UX Observations (voice)

- **UX-16 (MEDIUM) — The "Listening…" spinner also covers the transcription round-trip, so there's no "now processing" cue.** `app.py:96-98` shows `st.spinner("Listening... (up to 5s to start speaking, up to 10s of speech)")` around the *entire* `try_listen_via_mic()` call — which includes both the mic capture **and** the subsequent Groq Whisper upload/transcription (`stt.py:66-89`). So after the user stops talking, they still see "Listening…" while audio is actually being uploaded and transcribed, with no distinct "Transcribing…"/"Got it, thinking…" transition. Users may keep talking (nothing is recording anymore) or assume it froze. A clean fix pairs with R-20.
- **UX-17 (LOW–MEDIUM) — No real "recording" affordance.** The only feedback that the mic is live is spinner *text*; there's no level meter, waveform, pulsing dot, or countdown. Combined with server-side capture (below), a user has no confidence the mic is actually hearing them until the result (or "I didn't catch that") comes back seconds later.
- **UX-18 (LOW) — Voice is server-side only, and the toggle no longer says so.** Both capture (`voice_input.py` docstring: server-side mic) and playback (pygame on the host) run on the **machine hosting Streamlit**, not the user's browser/device. Round 2's R-9 relabeled the toggle from "🔊 Speak responses aloud (server audio)" to "🔊 Read replies aloud" — dropping the one hint that told users *where* the audio comes from. Fine for the intended localhost demo, but at mobile width the 🎤 Speak button renders and is tappable (confirmed live — controls lay out cleanly, no console errors) while doing nothing useful on a real phone: it would record the *server's* mic, not the phone's. A small "plays on this computer's speakers" help hint restores the lost context without reintroducing dev jargon.

### New Recommendations

#### High priority

**R-17. ✅ IMPLEMENTED (2026-07-16). Make TTS non-blocking and add a Stop control (fixes QA-13).**
Stop busy-waiting in the request thread. Two complementary options: (a) simplest — play the generated audio **in the browser** via `st.audio(mp3_bytes, autoplay=True)` instead of server-side pygame, which is inherently non-blocking and also fixes the server-only limitation (UX-18); or (b) if keeping server playback, run it on a background thread and return immediately, exposing a persistent "⏹ Stop speaking" button that calls `pygame.mixer.music.stop()`. Either way the UI must stay responsive during playback and the user must be able to cut the voice off.
**Gemini/Groq quota impact:** none — playback/threading only, no model calls.
*Implementation:* went with option (a). `phase3/tts.py`'s `TTS` class split generation from playback: new `synthesize(text) -> (audio_bytes, mime_type, backend) | None` generates edge-tts mp3 (or falls back to pyttsx3 wav) without ever touching pygame, returning raw bytes. `phase6/app.py` no longer gives `agent.tts` a `"speak"` mode at all (`agent.tts = None` unconditionally) — voice output is handled entirely outside `process_turn()`, in a new `_play_reply_audio()` called right after the reply is appended to the transcript, rendering via `st.audio(audio_bytes, format=mime, autoplay=True)`. This is architecturally cleaner than a stop button on a background thread: `st.audio()`'s player has native browser pause/seek controls for free, and there's no pygame/Streamlit-thread interaction to get wrong. The old `speak()` method (still used by the CLI REPL, `phase3/main.py --voice`, where blocking is actually correct) now calls `synthesize()` internally and plays the bytes via `pygame.mixer.music.load(io.BytesIO(...))` — a cleaner reuse that also means the CLI path leaves zero temp files behind at playback time (folds in most of R-21/QA-16 too).
*Verified live via Playwright, not just unit tests* (this is an architecturally significant change — server-side blocking playback replaced with browser-side async playback — warranting real browser confirmation, not just code review): drove the actual app through a full build+narrate+speak cycle with "Read replies aloud" on. A native `<audio>` element rendered (confirmed a real 18-second clip). Installed a JS `setInterval` timer directly on the page (200ms tick) before confirming the build — it ticked 464 times over ~90 seconds with a max gap of 215ms between ticks, direct proof the browser tab's own event loop never froze (a genuinely blocked tab would show multi-second gaps, not consistent ~200ms ticks). A screenshot caught the "Thinking..." spinner for a *new* turn actively running while the *previous* turn's audio player was still mid-playback (0:05/0:18, pause icon visible) — direct visual evidence that server-side processing and browser-side audio are now fully decoupled, the exact opposite of the old busy-wait behavior. Zero console errors across every test run. Confirmed no regression: Phase 3's full suite (7/7 agent + 4/4 narrator, exercising `agent.py`'s CLI-facing code paths) and Phase 6 (5/5) both pass clean after the refactor.

#### Medium priority

**R-18. ✅ IMPLEMENTED (2026-07-16). Differentiate STT failure causes and stop leaking raw exceptions (fixes QA-11 & QA-12).**
Have `_from_mic`/`_transcribe_groq` distinguish (i) *no speech captured* → "I didn't catch that — try again or type it below", (ii) *transcription service failed* (Groq error/timeout/429) → "Voice typing is unavailable right now — please type your message", and (iii) *mic unavailable* → a fixed friendly line with the technical errno logged **server-side only** (mirror the R-5 email-copy fix). This prevents users from re-recording into a dead service and burning Whisper quota.
**Groq quota impact:** slightly *reducing* — steers users to text on a real outage instead of repeat mic attempts. No added calls.
*Implementation:* `phase3/stt.py`'s `STT.listen()` kept its original never-raises `str`-returning contract (still used unchanged by the CLI REPL) but gained a new `listen_detailed()` returning `(transcript, failure_reason, possibly_truncated)`, with `failure_reason` one of `None`/`"no_speech"`/`"transcription_failed"` — a real, structural distinction now propagated from `_from_mic()`'s two genuinely different except branches (a `WaitTimeoutError` vs. any exception from the Groq call), not inferred after the fact. `phase6/voice_input.py`'s `try_listen_via_mic()` (and its new split siblings, see R-20) translate each `failure_reason` into its own fixed, friendly message — three module-level constants shared across every mic entry point so the wording can't drift between the all-in-one and split-phase paths — and the raw exception from a genuine mic/hardware failure is now only ever `print()`-ed server-side, never interpolated into the user-facing string (closing QA-12 in the same pass, since it's the same code path).
*Verified:* injected stub `STT`-like objects simulating each of the three failure modes directly through `try_capture_mic_audio()`/`try_transcribe_audio()` — confirmed the silence message and the service-failure message are genuinely different strings (previously identical), and confirmed a raw `OSError("...Errno -9996...")` never appears in the returned message. Updated `phase6/test_phase6.py`'s T-6.7 to assert the raw exception text is absent (a real, previously-unenforced gap in that test) alongside the existing friendliness check. Full regression: Phase 3 7/7 agent + 4/4 narrator, Phase 6 5/5 — all clean.

**R-19. ✅ IMPLEMENTED (2026-07-16). Signal the offline-voice fallback in the UI and fix the pyttsx3 reuse (fixes QA-14 & QA-15).**
When `speak()` falls back to pyttsx3, set a small session flag so `app.py` can show a one-line caption ("Using the offline voice right now — reconnect for the natural voice"). Separately, avoid the persisted-engine `runAndWait` pattern: initialize a fresh pyttsx3 engine per utterance (or otherwise guard against the known second-call hang) so the offline voice works on every reply, not just the first.
**Quota impact:** none (no API).
*Implementation:* rather than a session flag, `TTS.synthesize()`'s new return shape already includes which backend produced the audio (`"edge-tts"` or `"pyttsx3"`) — `app.py`'s `_play_reply_audio()` checks this directly and shows the caption only when it's `"pyttsx3"`, no extra state needed. Separately, `_generate_pyttsx3_wav()` was rewritten to call `pyttsx3.init()` fresh every time instead of reusing `_get_pyttsx3_engine()`'s cached module-global engine (removed entirely) — eliminates the known Windows SAPI5 failure mode where a persisted engine's second+ `runAndWait()` call can hang or go silent.
*Verified:* called the fallback generation method twice in direct succession (the exact scenario the old cached-engine bug would surface in) — both calls returned real, non-trivial audio bytes (132KB then 128KB), confirming no hang or silent second call. Verified the full chain end-to-end: forced `_generate_edge_mp3` to raise, confirmed `synthesize()` correctly fell through to pyttsx3 and returned `backend="pyttsx3"`, and that the resulting wav bytes play back cleanly. Full regression: Phase 3 7/7 + 4/4, Phase 6 5/5 clean.

**R-20. ✅ IMPLEMENTED (2026-07-16). Handle long speech and split the capture/transcription feedback (fixes QA-10 & UX-16).**
Relax `phrase_time_limit` (with a sane max, e.g. 20–30s) or detect a phrase-limit cutoff and tell the user their input may have been clipped. And change the mic flow to show two states — "🎤 Listening…" during capture, then "✍️ Transcribing…" during the Groq round-trip — so the user knows recording has stopped and processing has begun.
**Groq quota impact:** none (a longer allowed phrase is still one Whisper call; slightly larger audio payload only).
*Implementation:* `phase3/stt.py`'s `phrase_time_limit` raised from 10s to a new `PHRASE_TIME_LIMIT_SEC = 25` constant. Truncation detection computes the *real* captured-audio duration from the returned `AudioData` (`len(frame_data) / (sample_rate * sample_width)`, not a guess) and flags `possibly_truncated=True` when it runs within 0.5s of the limit — surfaced as a caption ("Your input may have been cut off...") without silently sending a clipped request. For the feedback split, `_from_mic()` was refactored into two independently-callable methods — `capture_mic_audio()` (recording only) and `transcribe_audio(audio)` (the Groq round-trip only) — with `_from_mic()` itself now just calling them in sequence (used by the CLI, which doesn't need split feedback). `phase6/voice_input.py` gained matching `try_capture_mic_audio()`/`try_transcribe_audio()` wrappers, and `app.py`'s mic handler now wraps each in its own `st.spinner()` — "🎤 Listening..." during capture, "✍️ Transcribing..." only once capture has actually stopped.
*Verified:* constructed a fake `AudioData`-shaped object sized to exactly hit the 25s limit and confirmed `possibly_truncated` correctly returns `True`; confirmed a normal-length capture returns `False`. Confirmed the two-phase spinner code path directly (not able to click a real "Speak" button live — this test machine has 26 mic devices and a real click would record ambient audio and spend Whisper quota, same discipline the review itself used). Full regression: Phase 3 7/7 + 4/4, Phase 6 5/5 clean (T-6.7 updated for the new 3-tuple return shape, still passing).

#### Low priority

**R-21. ✅ IMPLEMENTED (2026-07-16). Temp-file cleanup, a recording indicator, and restore the audio-location hint (fixes QA-16, UX-17, UX-18).**
Wrap the temp-mp3 lifecycle in `try/finally` so it's removed even when playback raises. Add a lightweight recording affordance (a pulsing "● Recording" caption/countdown beats a bare spinner). And add a `help=` tooltip on the "🔊 Read replies aloud" toggle noting the audio plays on the computer running the app — recovering the context R-9 removed without the "(server audio)" jargon. (If R-17 option (a) moves audio into the browser, the UX-18 part of this becomes moot.)
**Quota impact:** none.
*Implementation:* both `_generate_edge_mp3()` and `_generate_pyttsx3_wav()` wrap their temp-file writes in `try/finally`, so a file is removed on every path, success or failure — previously only the success path cleaned up. Added a pulsing red "● Recording" indicator (`st.empty()` + a small inline CSS `@keyframes` animation) shown for the duration of mic capture, cleared once it stops. For the audio-location hint, R-17's browser-playback move made the *old* wording moot exactly as this recommendation anticipated — rather than a stale "(server audio)" label, the checkbox's `help=` tooltip now says "Plays right here in your browser after each reply," which is genuinely accurate post-R-17, not just recovered context.
*Verified:* directly measured the system temp directory before/after a full edge-tts-fails-then-pyttsx3-fallback-then-play cycle — zero leaked files. Recording indicator and tooltip icon both confirmed rendering live via Playwright screenshot. Full regression: Phase 3 7/7 + 4/4, Phase 6 5/5 clean.

### New QA Finding

#### QA-17 (MEDIUM) — Real POI photos are fetched into the dataset, then silently dropped before they can ever be shown

### New UX Observations (travel-industry benchmark)

- **UX-19 (HIGH) — The product is text-only in a photo-first category.** The built itinerary (`r4_03_built_desktop.png`) is a wall of text bullets for Humayun's Tomb, India Gate, Red Fort and Qutab Minar — arguably the most photogenic monuments on earth — with not one image. Every benchmark competitor makes a destination *feel* like somewhere you want to go via photography; here there is no emotional pull and no sense of place. - **UX-22 (MEDIUM) — Information architecture buries the trip and leads with logistics.** Each day opens with the **emergency line (nearest hospital/pharmacy/metro)** in full-contrast text *above* the actual attractions (`r4_03_built_desktop.png`) — safety logistics shouldn't be the first thing a traveler reads about their day. ## 8. Voice-First Prioritization (round 5, 2026-07-16)

**Reviewer role:** Product Manager with voice-UI expertise, benchmarking against voice-first interfaces (Google Assistant, Siri, ChatGPT voice mode, Alexa app).
**Lens (new vs. rounds 1–4):** round 3 fixed voice *mechanics* (non-blocking TTS, differentiated STT errors, two-phase Listening/Transcribing spinners, a recording dot, raised phrase limit) — none of that is re-reported. This round is purely about the **visual and interaction priority between voice and text**: the project brands itself "voice-first" in its own architecture docs, but nothing in the current layout signals that to a first-time user. The app is, visually, a chatbot with a mic button bolted on beside Send.
**Method:** Drove the live app at `http://localhost:8501` with Playwright (existing server on 8501, left running — did not launch a second instance). Captured the current empty/onboarding state (`…/scratchpad/qa-review-phase2/r5_01_empty_desktop.png`, `r5_03_mobile.png`) and **measured the actual button geometry** rather than eyeballing it. Cross-read the current `phase6/app.py` input-row and sidebar code.
**Constraint discipline:** every recommendation keeps text input fully functional and equally reachable (never removed, never made harder), and assumes **press-to-talk** only — mic capture is server-side on a local Streamlit deploy, so nothing here relies on browser-native always-listening or wake-word detection that would need real re-architecture.
**Quota note:** this round spent **zero** LLM/STT calls (empty-state inspection + geometry measurement only, no build). None of the recommendations below add any LLM/STT calls — they are layout, styling, a default-value change, and copy. ### New UX Observations (voice-first priority)

- **UX-27 (HIGH) — Send and Speak are pixel-for-pixel co-equal, with the text action in the primary slot.** The input row builds the two buttons with `st.columns([1, 1])` and both as plain `form_submit_button`s (`app.py:110-112`). Measured live: **Send** is at x=396, width=466px; **🎤 Speak** at x=878, width=466px — *identical* width, identical 40px height, on the same row, with **Send occupying the left/primary reading position** and neither button using the app's saffron `primaryColor` accent (both render as default outline buttons). Nothing gives voice visual dominance; if anything the left-position text button reads as primary. A voice-first product makes the mic the single dominant control (large, centered, brand-colored), not a right-hand twin of Send.
- **UX-28 (HIGH) — The first impression is "type to me," and the mic sits below the fold.** The input area leads with a full-width `text_input` labeled "Talk to your travel assistant" carrying a *typed* placeholder ("Plan a 2-day trip to Delhi…", `app.py:107`) — the eye (and any cursor) lands on a text box. Worse, on the empty/onboarding screen the entire input row renders **at the very bottom of a long page**, beneath the hero photo, tagline, capability list, example chips, and the quick-options expander (`r5_01_empty_desktop.png`) — so the mic is literally the last thing a user reaches. - **UX-29 (MEDIUM) — Voice *output* is off by default and buried in the sidebar.** "🔊 Read replies aloud" is an unchecked checkbox inside the (collapsible) sidebar (`app.py:72-75`), so the default experience is **silent text replies**, and most users will never discover spoken output at all. A voice-first product either defaults spoken replies on or surfaces the control prominently next to the input — not tucked in Settings behind a panel many users never open.
- **UX-30 (MEDIUM) — There is no idle voice presence and no unified voice-state identity.** Round 3's recording dot and two-phase spinners only exist *during* a capture the user already initiated. In the **idle** state there's no inviting mic affordance, no "tap to talk" cue, and across the full idle → listening → transcribing → thinking → speaking lifecycle there's no single, consistent voice indicator (the orb/waveform/pulse that Siri, ChatGPT voice mode, and Assistant use to make voice feel alive and ever-present). Voice only appears as transient text spinners, then disappears.
- **UX-31 (MEDIUM) — Real-estate is allocated against voice.** Text gets a full-width row (the `text_input`); the mic gets *half* of the button row beneath it. So voice literally occupies less screen space than text, the inverse of a voice-first hierarchy where the mic is the largest interactive element.
- **UX-32 (LOW) — Onboarding never invites the user to speak.** The hero tagline, the "Here's what I can do" list (`app.py:466-472`), and all three example chips are text-framed; none says "just tell me out loud" or "tap the mic and describe your trip." A first-time user is never told voice is even the intended primary mode, let alone nudged toward it.

## 9. Listening Indicator (user request, 2026-07-16)

**Request:** *"When the [user] speaks using the voice button, add a display that the application is 'listening' at a suitable location."* — a direct implementation request, not a review round.

**What I found (drove the code, didn't assume):** a "listening" indicator already existed from round 3 — a pulsing red "● Recording" dot (R-21) plus a two-phase "🎤 Listening… / ✍️ Transcribing…" spinner (R-20) inside `app.py`'s `if mic_clicked:` block. But it was **in the wrong place.** That block runs at top level *after* `st.columns()` is called, and — per the very render-order quirk this codebase already documents for the input row (a placeholder/element anchors where it is *declared*, and un-columned elements declared after `st.columns()` render below all column content) — the dot and spinner surfaced at the **bottom of the page**, far below the fold from the large "🎤 Tap to talk" button (round 5, R-29) the user had just tapped at the top. So the app *did* signal listening, but nowhere the user was looking. My judgment: this is exactly what the request is about — not a missing indicator, but one in an unsuitable location — so the right fix is to **relocate and strengthen the existing indicator**, not add a redundant second one (which the task explicitly cautioned against).
